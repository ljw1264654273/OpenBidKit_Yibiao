标书项目管理
从「一次写一个」到「多标书并行管理」

当前客户端一次只能承载一个标书撰写流程，历史标书没有独立载体。本需求将标书升级为可持久化、可检索、可随时续写的项目实体，并在源文件层与生成内容层建立双层防重机制：同一招标文件不重复立项，同一项目下多方生成的正文保持可区分的原创性。

1背景与业务诉求

现状缺口

当前客户端一次只能进行一个标书的撰写流程，生成的标书没有独立载体，无法回溯、无法并行处理多个投标项目。用户重新进入或新建流程后，历史标书的目录、正文、全局事实等中间产物即丢失或被覆盖。

业务痛点

  • 投标专员通常同时跟进 2–5 个项目，现有流程只允许串行处理，切换即中断；
  • 撰写到一半的标书无法保存为“可继续的项目”，中断后需要重跑解析流程；
  • 历史标书无法沉淀为资产，同类项目的目录与正文无法复用；
  • 缺少统一入口感知“手上有哪些标书、各自走到哪一步”；
  • 同一份招标文件被反复上传、重复生成标书，产生多份内容雷同的产物，既占用存储也无法分辨哪一份是最新、该继续跟进哪一份；
  • 同一项目由多方分别生成标书时，正文表达高度雷同，在招投标场景下存在被认定为串标围标的风险，缺少可量化的原创性校验手段。
一句话需求原文 “当前项目只能一次写一个标书，我希望可以管理自己生成的标书。”
“生成的标书需要考虑智能防重，同一个招标文件生成的标书要能识别出来。”
“基于内容指纹技术，确保多用户对同一项目的生成具有原创性，避免重复。”

2目标与成功度量

业务目标

  1. 支持多个标书项目在同一工作区内并存，数据互不干扰；
  2. 用户可随时回到任意历史标书，查看状态或继续未完成的撰写流程；
  3. 把标书沉淀为可检索、可复用的项目资产，降低同类项目的重复投入；
  4. 同一份招标文件不产生重复标书，重复上传时引导用户回到已有标书而非再生成一份；
  5. 同一用户先后生成的多份标书之间正文不重复，避免同一项目下不同标段的标书写成雷同内容。

成功度量

指标基线目标值说明
可并存标书数量1 个≥ 20 个在此规模下列表与打开操作无明显性能劣化 待确认
标书找回耗时不可找回≤ 2 次点击从进入应用至打开目标标书
流程中断率—下降因“切换标书导致进度丢失”造成的中断 待确认：基线采样方式
重复标书数量不可控0 份同一招标文件未经用户显式确认，不产生第二份标书
重复文件识别率—100%完全相同的招标文件重复上传时必须命中 待确认：判定层级先做文件摘要还是同时做正文指纹
标书正文重复度不可控经处理后可接受同一用户多份标书之间的重复段落被全部标出并处理 待确认：相似度判定口径

3用户角色与关键场景

角色职责使用频率
投标专员新建标书、跟踪生成进度、继续编辑、导出交付高（每日多次）
标书负责人 待确认：是否存在该角色查看全部标书状态、汇总进度中

主流程

新建标书（上传招标文件，支持 .doc / .docx / .pdf，可一次性上传多个文件）→ 上传即触发防重校验（见 F-10）→ 命名并确认 → 进入撰写流程 → 列表实时新增卡片，状态随流程推进变化 → 完成后可导出。

回访流程

从列表打开历史标书 → 查看状态、方案类型与正文预览 → 继续编辑或导出交付。

异常分支

（1）上传的招标文件命中已有源文件时，转入防重提示分支，用户可选择打开已有标书或带标段标识放行（见 F-10）。

（2）生成中断或失败的标书在列表中标记异常状态，支持重试或删除。待确认：失败诊断展示到什么粒度

4功能需求清单

编号功能描述优先级要点
F-01 标书列表：卡片式展示工作区内全部标书，含名称、状态标签（生成中 / 未完成 / 已完成 / 生成失败）、方案类型（技术方案 / 完整方案）、创建时间；首屏常驻“新建标书”卡片 Must 默认按更新时间倒序；超长名称截断并支持悬浮查看全称
F-02 新建标书：从新建卡片上传招标文件，创建独立标书项目并进入撰写流程 Must 支持 .doc/.docx/.pdf；多文件一次上传；文件不合法给出明确提示；上传即触发防重校验（见 F-10）
F-03 打开与续写：点击卡片进入该标书详情，目录、正文、全局事实等中间产物完整恢复 Must 与上次退出时的内容一致；可同时打开多个标书 并发生成策略待评估
F-04 状态筛选：顶部 Tab 按「全部 / 已完成 / 未完成」过滤列表，异常态可单独筛出 Must 筛选结果为空时展示空态引导，而非空白页；状态枚举含生成中与生成失败为已确认决策
F-05 类型筛选 + 名称搜索：按方案类型下拉筛选；按方案名称关键字实时搜索 Should 本地查询，输入即时过滤
F-06 卡片操作菜单：重命名、删除、导出 Word / PDF Should 删除为直接删除、不进回收站（已确认），但须二次确认并明确提示影响范围
F-07 视图切换：卡片视图 / 列表视图切换，并记住用户偏好 Could 偏好仅存本地 UI 设置
F-08 生成失败标记与重试：生成中断或失败的标书在列表中标记为异常态，支持重新生成 Should 与现有 Agent 失败诊断能力衔接 待确认：诊断信息展示粒度
F-09 进度可见性：列表卡片直接展示当前所处阶段（如“招标文件解析”“大纲已生成”“正文部分预览中”） Should 不进入详情即可判断每个标书走到哪一步
F-10 智能防重：上传招标文件时自动与已有标书的源文件比对，识别“同一招标文件”并阻止重复生成，引导用户打开已有标书；用户确需另建（如多标段投标）时可显式放行 Must 默认不创建重复项目；命中后给出来源标书与创建时间；放行须填写标段 / 包件标识
F-11 正文内容防重（内容指纹）：基于内容指纹检测本机已有标书的正文，识别新生成标书中与既有内容重复的段落，标出重复位置并给出改写建议，由用户确认后替换 Must 比对范围限本人本机标书；只提示不自动改写；典型场景是同一招标文件下多标段标书之间的正文雷同

F-10 智能防重 · 判定规则与命中处理

判定层级依据命中口径
L1 文件摘要文件内容摘要（非文件名）完全一致 → 强命中，直接提示
L2 正文指纹解析后正文文本归一化（去空白、页眉页脚、页码）后比对文件字节不同但正文一致（如重新下载、另存）→ 命中
L3 元信息文件名、页数、招标编号、项目名称仅作提示与展示，不单独作为判定依据

多标段放行规则

  • 同一招标文件含多个标段 / 包件、用户需分别投标时，允许在同一源文件下生成多份标书；
  • 放行时须填写标段 / 包件标识，系统在标书名称后自动追加标识（如“XX 项目技术方案-标段二”），避免列表中出现多份无法分辨的同名标书；
  • 同一源文件下的多份标书标记为“同源标书”，列表中可互相跳转查看 待确认：是否需要同源分组视图；
  • 再次上传同一源文件时，提示中一并列出该源文件下已有的全部标书及其标段标识。
设计边界 防重是“识别 + 提示 + 显式确认”，不做硬拦截。多标段是真实业务场景，一刀切禁止会迫使绕过流程（如改文件名），反而让防重失效。

F-11 正文内容防重 · 检测范围与结果呈现

比对范围范围定义是否纳入
本人本机标书同一客户端内我自己生成过的全部标书（跨项目）纳入
同一项目标书同一招标文件 / 同源标书下的其他标书（重点场景：多标段）纳入，重点提示
他人及其他设备其他用户、其他电脑上生成的标书不纳入（本期已确认）

重复程度分级与处理

  • 低重复：与既有内容基本无重叠，正常放行，不做打扰；
  • 中重复：存在部分段落表达接近，标注位置并给出改写建议，用户自行决定是否替换；
  • 高重复：存在整段级重复，显著提示并附带改写建议，建议处理后再导出 待确认：是否允许带着高重复段落导出。

边界说明

  • 本能力只检测文本表达层面的重复，用于保证多份标书之间的可区分度，不等同于著作权意义上的原创性判定；
  • 系统只做检测与建议，不自动改写正文，最终是否替换由用户确认（已确认决策）；
  • 检测结果需能在正文中直接定位到段落，避免用户拿着一个总分却找不到改哪里 待确认：是否需要导出重复清单。

5非功能需求

  • 性能：列表加载与筛选为本地查询，20 个标书规模下交互无明显卡顿 待确认：建议 P95 < 500ms；并发生成策略见第 9 节评估结论——所接 DeepSeek 官方 API 并发配额充足，建议以有限并发（建议上限 2–3）实现，避免极端场景下打满账号配额
  • 安全：标书数据全部保存在用户本机工作区，不新增对外上传链路
  • 合规：招标文件与标书正文属敏感业务资料，删除操作须二次确认并明确提示影响范围（已确认：直接删除、不进回收站）待确认：是否需要操作留痕
  • 可用性：列表页在无标书、筛选无结果、生成失败三种状态下均有明确引导文案
  • 兼容性：与现有客户端渲染层保持一致，长列表在低配置机器上不阻塞主线程

7范围边界

In Scope（本期做）

  • 标书项目的持久化与项目隔离
  • 列表管理（状态 / 类型 / 搜索 / 视图切换）
  • 打开续写、重命名、删除、导出
  • 生成失败态标记与重试
  • 同一招标文件的智能防重与多标段放行
  • 本机本人标书之间的正文内容防重（内容指纹检测 + 改写建议）

Out of Scope（本期不做）待确认

  • 多人协作 / 标书共享
  • 文件夹、标签等分组归类
  • 跨用户、跨设备的正文比对与共享内容库
  • 正文自动改写降重（本期只检测 + 建议，不自动改）
  • 跨工作区迁移与云端同步
  • 基于历史标书的模板库沉淀
  • 标书正文层面的内容查重（防重仅针对源招标文件）

8数据与实现要点 需开发确认

本需求的主要工作量集中在数据层，而非列表界面。现状流程状态为单例结构，需改造为按标书项目隔离。

  • 新增实体：标书项目（名称、状态、方案类型、创建 / 更新时间、关联的招标文件与产物）；
  • 存储位置：权威存储落在工作区 SQLite，与本项目现有约定一致；
  • 状态机：现有单流程状态需拆分为“标书维度”的状态，状态枚举含生成中与生成失败（已确认），列表状态标签与详情状态同源；
  • 后台任务：解析、目录、正文等耗时流程需绑定到具体标书项目，页面卸载不影响任务推进；多标书的并发生成策略待评估；
  • 历史数据：本期不做存量迁移，现有标书不迁入列表（已确认）；
  • 源文件防重所需字段：标书项目需持久化源招标文件摘要（内容摘要值与正文归一化指纹）、来源文件名 / 页数 / 招标编号等元信息、标段 / 包件标识，以及同源标书之间的关联关系；
  • 正文防重所需数据：需保存标书正文的段落级内容指纹，作为后续跨标书比对的比对库；比对范围限本机本人（已确认），不涉及共享指纹库；
  • 比对的时机与代价：源文件摘要比对在上传时同步完成，成本极低；正文指纹比对依赖解析与生成结果，应复用现有产物，避免为防重额外跑一轮解析。
评审提示 建议需求评审时拉开发一起过本节。若项目隔离模型未同步改造，仅完成列表 UI 会导致“列表有多条、点进去内容互相覆盖”的伪需求实现。

9依赖、风险与待确认项

类型内容影响 / 缓解
依赖现有招标文件解析、大纲生成、正文生成与导出能力需全部支持按标书项目维度调用
依赖工作区 SQLite 存储与后台任务调度改造范围评估的前提
依赖所接模型服务的并发配额已核实：DeepSeek 官方 API 并发按账号计，deepseek-v4-pro 500、deepseek-v4-flash 2500，超出返回 429；同时写 2–5 份标书远在配额内，不构成瓶颈
风险本期不做存量迁移，现有正在撰写的那份标书不出现在列表中需在列表页给出说明入口，避免用户误以为标书丢失
风险多标书并行后台任务打满账号并发配额（并发按账号计，与 API Key 无关，多人共用账号时共享额度）已评估：DeepSeek 官方配额为 pro 500 / flash 2500 并发，本场景仅需个位数；仍建议设并发上限，超出排队
风险并行降低上下文缓存（KVCache）复用率，多份标书同时发起时 token 成本可能略升并发上限设为 2–3 可兼顾耗时与缓存复用
风险长请求等待：10 分钟未开始推理服务端会断开连接，需与普通超时区分处理需实现保活识别与失败退避重试，避免任务被判为生成失败
风险正文重复判定过严，把正常引用的规范条文、招标文件原话也标为重复需明确豁免范围（如必须逐字引用的条款） 待确认
风险防重误判：不同招标文件（如同一项目不同标段的独立文件）被判定为重复，干扰正常创建判定仅在高置信时触发，且命中后只提示不拦截，用户可放行
风险同一源文件下多份标书在列表中难以分辨名称自动追加标段 / 包件标识，并关联同源标书
待确认源文件防重的判定层级：先只做文件摘要，还是同时做正文指纹直接决定能否覆盖“重新下载导致字节不同”的实际场景

  • 数据模型改造方案：现状单流程状态如何拆分为按标书项目隔离。影响最大，建议由开发先评估再定稿。
  • 源文件防重判定层级：本期只做文件摘要，还是同时做正文指纹。建议两者都做——只做文件摘要会漏掉“从招标平台重新下载、字节不同但内容相同”这一最高频的重复场景。
  • 正文重复判定口径：多大的重合算“一段重复”、相似度用什么衡量、必须逐字引用的规范条文是否需要豁免。直接决定验收标准与误报率。

  • 同源标书展示：同一招标文件下多份标书是否需要分组视图，还是仅在提示中列出即可。
  • 成功度量基线：20 个标书规模、2 次点击找回、重复标书 0 份、正文重复段落经处理后可接受，是否认可为验收指标。
  • 范围边界：Out of Scope 六项（协作 / 分组 / 跨用户比对 / 自动改写 / 迁移同步 / 模板库）是否本期确认不做。
