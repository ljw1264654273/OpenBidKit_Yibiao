# 历史标书适配一致性检查自动修复设计

## 背景与目标

历史标书适配的“运行一致性检查”目前只检查迁移后的正文并生成问题，不会自动改写正文。用户希望点击该入口后，AI 自动处理能够从当前招标基线和全文事实中确定的改写，无法安全判断的内容再交给人工处理；尤其要避免只修复单章后，全文出现工作量、地点、工期、阶段或服务范围前后不一致。

目标是把现有一致性检查扩展为一次受控的“检查 → 全文事实归一 → 自动修复 → 全文复查”流程，同时保持现有按钮、后台任务和阶段确认门禁不变。

非目标：不自动覆盖人工正文；不对结构性数据缺失、来源快照失效或空正文进行猜测式生成；不新增独立的用户入口或在线服务协议。

## 设计决策

### 处理入口与任务边界

继续使用现有 `startHistoricalAdaptationContentCheck` IPC 和 `historical-adaptation-content-check` 受管任务。任务内部增加明确阶段：

1. 确定性预检。
2. 提取招标基线与全部章节的统一事实表。
3. 语义一致性检查。
4. 生成并校验自动修复候选。
5. 原子应用可安全修复的候选。
6. 重新提取事实并复查，最多两轮自动修复。

任务完成后仍需用户点击“确认本阶段”，不会因为自动修复成功而自动确认阶段。

### 全文事实口径

AI 检查和修复使用同一份事实表，事实至少包含：实施地点、实施对象、工作量、金额（如正文涉及）、开始/结束日期、工期、阶段节点、服务范围、关键名称及其原文证据。跨批次正文先生成带章节 ID 的事实证据，再由跨批次请求归一出当前招标基线下的统一口径。若同一事实存在无法消解的冲突，不生成自动修复，保留为人工问题。

事实表只作为当前检查任务的内存/任务上下文，不在 Renderer 保存平行业务状态；最终权威内容仍是 `technical_plan_outline_nodes.content` 和历史适配内容 Store。

### 自动修复范围

自动修复只针对 `content_origin` 为迁移生成、局部改写或 AI 改写的章节。`manual` 来源章节只参与检查，不自动覆盖。

AI 只能返回结构化的局部替换候选，不返回整章自由改写。候选包含：问题 ID、目标章节 ID、唯一 `old_text`、`new_text`、统一事实 ID、修复依据和置信度。只有满足以下条件才允许写入：

- `old_text` 在目标章节中唯一命中；
- 新旧文本确实不同，且编辑之间不重叠；
- `new_text` 符合当前事实表，并且不引入已确认的历史残留或删除内容；
- 同一跨章节事实的所有关联章节均可形成一致替换；
- 正文哈希在生成候选到提交前未变化。

地点、日期、工作量、工期等精确事实优先使用结构化确定替换；服务内容等需要语义改写的内容必须限制在 AI 返回的唯一片段内，不能扩写、润色或修改未授权事实。

### 结构性问题与人工回退

下列问题不交给 AI 猜测，直接转人工：来源快照不可用、迁移方案/结果指纹失效、章节记录缺失、空正文、人工正文、无法唯一定位原文、事实冲突无法闭合，以及 AI 返回不合法或复查失败。

自动修复以“编辑组”为原子单位。跨章节问题的任一关联章节校验失败，整组不写入。AI 服务异常、结构化响应校验失败或正文哈希变化时，原正文保持不变，检查任务不报告虚假的“检查通过”。

最多执行两轮自动修复。第二轮后仍有阻断的问题保留在检查结果中，并在 UI 标记为“需要人工处理”或“仍有阻断”。

### 正文来源与状态

自动修复成功后保留 `ai-repair` 来源标记，并更新对应的迁移输出指纹；内容写入会使旧一致性快照失效，当前任务随后写入带最新内容哈希和输入哈希的复查快照。人工编辑仍使用现有 `manual` 来源和保存协议。

## 数据流与模块

### Main 侧

- `historicalAdaptationContentCheckTask.cjs`：编排检查、事实归一、修复轮次、进度和最终检查快照。
- `historicalAdaptationConsistencyRepair.cjs`：规范化 AI 修复响应，执行唯一文本命中、编辑冲突、事实口径和残留校验，输出可应用修复组及人工回退原因。
- `technicalPlanStore.cjs`：提供多章节原子应用修复的 Store 方法，更新正文、内容来源、迁移输出指纹，清除旧确认和旧检查快照。
- 现有 `taskService.cjs`：继续负责受管任务生命周期和事件回放，不新增任务类型。

### Renderer 侧

- `src/features/technical-plan/types.ts`：增加 `ai-repair` 来源和自动修复统计/阶段字段。
- `AdaptationContentPage.tsx`：复用现有按钮和任务事件，展示“提取全文事实、自动修复、复查”阶段、自动修复数量和人工待处理摘要；问题列表继续支持点击定位章节。

### IPC 与 Analytics

不新增 Renderer/Main IPC 通道，仍调用现有 `startHistoricalAdaptationContentCheck`。不新增菜单或路由，不改变 Analytics Worker/Dashboard 协议；现有任务和页面埋点继续有效。

## UI 行为

按钮文案保留“运行一致性检查”。任务运行中按阶段显示：

- 正在提取全文事实；
- 正在检查跨章节口径；
- 正在自动修复第 N 轮；
- 正在复查全文。

完成后显示自动修复数量、仍有阻断数量和需要人工处理数量。自动修复成功的问题从当前阻断列表移除；未能安全修复的问题保留证据和章节定位。即使阻断清零，也必须手动点击“确认本阶段”；占位符继续沿用现有“确认保留并继续”流程。

## 测试与验收

### 单元测试

- 修复响应缺少字段、`old_text` 多处命中、编辑重叠、引入历史残留时必须拒绝应用。
- 人工正文不生成自动修复写入。
- 同一事实的多章节修复必须使用统一 `new_text`；任一章节失败时整组回滚。
- 自动修复成功后更新内容来源和迁移输出指纹。
- AI 服务异常或复查失败时原正文不变，结果转人工处理。
- 达到两轮上限后仍保留未解决阻断，不进入通过状态。

### 任务集成测试

- 确定性结构问题仍跳过 AI，不产生猜测式正文。
- 语义问题能够走“事实提取 → 修复 → 复查”流程并保存最新哈希。
- 修复后出现新的跨章节冲突时不报告成功。
- 缓存只在内容哈希、输入哈希和规则版本均匹配时复用。

### 工程验收

- `node --check` 检查新增/修改的 `.cjs` 文件。
- 定向执行历史适配一致性检查和 Store 测试。
- `cd client; npm run build` 通过；既有 chunk 体积警告不视为失败。
- 手动验证：AI 生成章节可自动统一口径，人工章节不被覆盖，失败项可定位并继续人工处理，确认阶段和导出门禁仍有效。
