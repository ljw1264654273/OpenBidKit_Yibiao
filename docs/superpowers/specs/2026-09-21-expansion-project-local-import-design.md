# 已有方案扩写独立项目与本地导入设计

## 1. 背景与目标

当前客户端将“生成技术方案”和“已有方案扩写”放在同一套技术方案工作区中，通过 `workflowKind` 切换。切换时会清理当前工作区的目录、全局事实、正文和生成进度，容易让用户误以为两种能力是同一份项目的不同模式，也存在误清理进度的风险。

本次改造的目标是：

- 用户点击“已有方案扩写”时，直接进入“新建扩写项目”。
- 本期扩写项目只支持导入本地招标文件和本地已有标书/原方案。
- 每次扩写都创建一份新的、独立的标书项目。
- 原技术方案项目不被修改、覆盖或实时依赖。
- 技术方案项目和扩写项目继续共用成熟的 Step 页面、任务体系和生成能力，但项目数据、任务、配置、正文、图片和导出上下文完全按项目隔离。
- 删除、重置或失败清理某一项目时，不影响其他项目。

本期不实现“基于系统内已有标书创建扩写项目”。该能力未来可以在不改变本次数据边界的前提下增加。

## 2. 用户流程

### 2.1 新建技术方案

“我的标书”中的“新建标书”继续创建 `technical-plan` 项目：

```text
我的标书
→ 新建标书
→ 选择本地招标文件
→ 创建技术方案项目
→ 进入技术方案工作区
```

现有技术方案项目的导入、生成、编辑和导出流程保持不变。

### 2.2 新建已有方案扩写

点击侧边栏“已有方案扩写”时：

```text
已有方案扩写
→ 新建扩写项目页面
→ 上传本地招标文件
→ 上传本地已有标书/原方案
→ 创建扩写项目
→ 进入扩写项目工作区
```

创建页面需要同时收集两类文件：

- 招标文件：允许与现有技术方案一致地选择一份或多份文件。
- 已有标书/原方案：本期支持一份本地文档，作为扩写底稿。

两类文件均解析成功且项目创建成功后，才进入扩写工作区。扩写工作区使用现有的技术方案步骤：

```text
招标文件与原方案
→ 招标文件解析
→ 扩写目录生成
→ 全局事实设定
→ 正文扩写
→ 图片处理与导出
```

系统可以在目录生成阶段根据新招标文件和原方案自动调整目录，但这属于生成策略，不新增用户必须理解的独立入口。用户仍然在现有目录页面确认和编辑目录。

### 2.3 继续已有扩写项目

“我的标书”列表中已经存在的 `existing-plan-expansion` 项目可以直接打开并继续。打开后只进入该项目自己的扩写工作区，不再出现“切换到已有方案扩写”确认框。

项目类型创建后固定：

- `technical-plan` 项目不能切换为扩写项目。
- `existing-plan-expansion` 项目不能切换为普通技术方案项目。
- 用户如果想使用另一种流程，应返回项目列表并创建新项目。

## 3. 项目与数据边界

### 3.1 项目类型

继续使用现有项目类型：

```text
technical-plan
existing-plan-expansion
```

`bid_projects.project_type` 是项目类型的业务权威来源。技术方案工作区中的 `workflow_kind` 作为兼容和任务上下文字段保留，但不得再作为同一项目内可切换的状态。

打开项目时，工作区加载的 workflow kind 必须与项目类型一致。旧数据迁移时：

- 普通项目保持 `technical-plan`。
- 已有 `original_plan` 数据或项目类型已经是 `existing-plan-expansion` 的项目按扩写项目恢复。
- 不删除已有正文、目录或原方案文件。

### 3.2 隔离范围

每个项目继续通过现有 `projectId` 隔离：

- 招标文件与其 Markdown；
- 原方案与其 Markdown；
- 招标文件解析结果；
- 目录和目录节点正文；
- 全局事实；
- 正文生成状态、计划和运行时；
- 图片、Mermaid 缓存及导出上下文；
- 本地和远程知识库选择；
- 后台任务、任务日志和恢复状态；
- 项目步骤、生成配置和失败状态。

项目之间只共享：

- 全局模型和应用配置；
- 知识库中的可复用资料本身；
- UI 轻量偏好；
- 任务系统和页面组件代码。

扩写项目导入的本地文件需要复制或解析到扩写项目自己的目录，不能继续引用用户临时选择路径作为运行时数据源。

### 3.3 来源关系

本期扩写来源全部为本地文件，因此不增加 `sourceProjectId` 或系统项目快照关系。扩写项目保存：

- 招标文件源记录；
- 原方案源记录；
- 原方案解析后的 Markdown；
- 文件 hash、解析器和导入时间。

未来支持“基于系统内标书扩写”时，再增加创建时快照和来源项目标识；不采用实时引用，避免原项目变化影响扩写项目。

## 4. 界面与导航

### 4.1 侧边栏入口

保留一级菜单“已有方案扩写”，但其含义固定为“新建扩写项目”，不再代表一个可切换的全局工作区。

没有活动项目时进入新建扩写页面；已有项目从项目列表打开时进入该项目对应的扩写工作区。

### 4.2 新建扩写页面

新增扩写项目创建页面，放在 `bid-project` feature 内，作为项目创建流程的一部分；创建成功后再进入 `technical-plan` feature 的扩写工作区。页面复用现有：

- `UploadBoard`、`UploadRow`、`UploadFilePill`；
- 文档解析提示；
- Toast；
- 文件拖拽路径解析；
- 本地 Markdown 预览。

页面至少包含：

- 招标文件导入区；
- 已有标书/原方案导入区；
- 两份文件的解析状态和 Markdown 预览；
- 项目名称输入，默认由招标文件名或原方案名推导；
- “创建扩写项目”按钮。

按钮在两类文件均解析成功前不可用。创建失败时清理本次暂存目录和已经创建的空项目，不能留下半成品项目。

### 4.3 技术方案工作区

从 `TechnicalPlanHome` 删除面向用户的工作流切换逻辑：

- 删除跨一级菜单切换时的“确认切换到已有方案扩写”弹窗；
- 删除“清空之前已有进度”的切换提示；
- 删除切换后清理另一种模式数据的行为；
- 项目上下文栏只展示当前项目名称、项目类型和当前步骤。

普通项目和扩写项目继续复用同一套页面，通过固定的项目类型决定扩写专属内容是否显示。

## 5. Main、IPC 与导入流程

### 5.1 扩写项目创建 API

增加独立的扩写导入服务流程，不把“先创建项目、再在页面分别上传”作为最终一致性方案。建议提供：

```text
prepareExpansionImport(tenderFilePaths, originalPlanFilePaths)
confirmExpansionImport(token, options)
discardExpansionImport(token)
```

`prepareExpansionImport` 负责：

- 解析本地招标文件和原方案；
- 暂存文件和解析元数据；
- 计算源文件 hash 与内容 hash；
- 返回预览信息，不创建正式项目。

`confirmExpansionImport` 负责：

1. 创建 `existing-plan-expansion` 项目；
2. 初始化该项目的技术方案 schema 和工作区；
3. 导入招标文件；
4. 导入原方案；
5. 确保工作区 `workflow_kind` 与项目类型一致；
6. 记录项目源文件；
7. 删除导入暂存目录；
8. 打开并返回新项目。

任一步失败都必须：

- 删除本次创建的项目；
- 清理该项目工作目录；
- 清理导入暂存目录；
- 返回可操作的错误提示。

### 5.2 IPC 边界

Renderer 只通过 `window.yibiao` 调用扩写项目导入 API。新增 preload API 时同步更新 `src/shared/types/ipc.ts`。

Renderer 不直接读写文件，也不直接调用 `fs`、`path` 或 `ipcRenderer`。

### 5.3 旧切换 API

`technical-plan:switch-workflow-kind` 不再被 Renderer 使用。实现阶段可以保留 Main 侧兼容入口用于旧调用或迁移，但其默认行为不得继续清理用户项目数据；最终可在确认无调用后删除。

## 6. 数据迁移与兼容

现有项目采用按 `projectId` 创建技术方案表的结构，本次不新建第二套平行数据库，也不迁移到“同一项目两份 workflow 数据”结构。

启动或打开项目时需要处理：

- `project_type` 与工作区 `workflow_kind` 不一致；
- 旧的无项目默认工作区；
- 旧的扩写工作区中已经存在原方案文件；
- 旧项目列表记录缺少完整状态。

迁移原则：

- 优先保留用户已有数据；
- 不能因类型修正清空目录或正文；
- 对扩写项目将 workflow kind 修正为 `existing-plan-expansion`；
- 对普通项目将 workflow kind 修正为 `technical-plan`；
- 旧默认工作区不直接删除，必要时保留为兼容读取对象，后续由用户创建正式项目。

## 7. 错误处理与状态

用户可见错误通过现有 Toast 和文档解析提示 Provider 展示，不使用 `alert`。

需要覆盖的错误场景：

- 只选择招标文件，未选择原方案；
- 原方案解析为空；
- 招标文件解析失败；
- 文件格式需要 LibreOffice；
- 暂存导入过期；
- 正式项目创建失败；
- 导入过程中某一步失败；
- 用户取消选择或取消创建。

导入过程中按钮和拖拽区域禁用，页面卸载不取消 Main 正在执行的导入事务；若 Main 任务最终失败，必须返回错误并完成清理。

## 8. 测试与验证

### 8.1 Renderer

补充测试确认：

- 点击“已有方案扩写”进入新建扩写页面，而不是打开默认共享工作区；
- 新建扩写页面要求招标文件和原方案同时存在；
- 创建后打开项目类型为 `existing-plan-expansion`；
- 普通技术方案项目和扩写项目打开后不出现模式切换弹窗；
- 两种项目仍复用同一套 Step 页面和扩写专属展示逻辑。

### 8.2 Main 与 Store

补充定向测试确认：

- 扩写导入成功后创建独立项目；
- 招标文件和原方案均保存到新项目目录；
- 扩写项目的目录、正文和任务不写入其他项目；
- 导入中途失败会删除项目和暂存文件；
- 重置或删除扩写项目不影响普通技术方案项目；
- 类型和 `workflow_kind` 不一致时优先保留内容并修正类型，不清空数据；
- 旧切换 API 不再清理项目业务数据。

### 8.3 必要命令

```powershell
cd client
node --check electron\services\bidProjectImportService.cjs
node --check electron\services\bidProjectStore.cjs
node --check electron\services\technicalPlanStore.cjs
node --check electron\preload.cjs
npm run build
```

涉及 SQLite Store、导入清理或 native 模块时，再运行：

```powershell
npm run smoke:electron-native
```

涉及窗口、导航和文件选择时，使用：

```powershell
npm run dev
```

手动验证新建普通项目、新建扩写项目、返回项目列表、重新打开两个项目、重置其中一个项目和导入失败清理。

## 9. 不在本次范围

- 从系统内已有标书创建扩写项目；
- 普通项目和扩写项目之间的内容复制；
- 项目间实时同步；
- 扩写项目的多份原方案合并；
- 新增第三种扩写模式；
- 重做现有目录生成、全局事实和正文生成算法；
- 删除共享的扩写 Prompt 和任务逻辑。
