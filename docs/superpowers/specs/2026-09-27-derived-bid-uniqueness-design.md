# 同源第二份标书差异化生成设计

## 目标

用户可以从一份已经完成的技术方案项目直接创建同源第二份标书。新项目复用同一招标文件及第一份标书中已经确认的招标分析结果，但必须重新生成目录和正文；正文完成后自动以现有“同源正文查重”算法与第一份标书比较，自动改写非豁免重复内容，直到查重结果为零才把项目标记为完成。

## 验收标准

- 入口只对已经完成、且存在有效招标文件和正文的普通技术方案项目开放。
- 新项目与来源项目属于同一 `source_group_id`，但拥有独立的项目目录、技术方案表和后台任务状态。
- 新项目复用招标文件、当前标段选择和成功的招标分析结果，不复制来源项目的目录、全局事实、正文、图片或生成任务。
- 新项目目录必须重新运行目录生成任务。来源目录仅作为排除参照，评分原文要求和固定响应层级仍优先。
- 正文全量生成成功后，以现有项目级同源查重的 `medium` 灵敏度执行自动查重。
- 招标原文及现有查重算法已经判定为豁免的内容继续豁免，不另建第二套规则。
- 自动处理完成条件为 `duplicateParagraphCount = 0` 且 `exactSentenceCount = 0`。
- 自动改写达到最大轮次仍有非豁免命中时，查重任务失败并保留已成功生成的正文及最终查重结果，不得把项目标记为完成。
- 派生项目正文被重新生成或手工修改后，既有通过状态立即失效；只有最新正文再次通过查重后才能完成和导出。
- 来源项目不被自动改写；所有自动改写只落到派生项目。

## 方案选择

### 采用：派生项目 + 生成后确定性闭环

创建带来源项目关系的独立技术方案项目，目录生成时提供来源目录作为禁止照搬的参照，正文生成完成后使用现有本地查重算法反复检测和改写。最终是否通过完全由本地算法决定，而不是由模型自报。

这一方案同时满足独立工作区、重新生成目录、自动消重和可审计验收，并最大限度复用现有项目管理、正文节点定位、查重结果存储和 AI 改写能力。

### 不采用：已有方案扩写

`existing-plan-expansion` 的职责是还原和扩充原方案，会主动复用原方案内容，与“第二份不得重复”的目标冲突。

### 不采用：只在提示词中要求不要重复

提示词只能降低首轮重复概率，不能提供确定性验收，也无法覆盖生成后的人工修改。因此仍必须以现有本地查重算法建立闭环。

## 数据模型

在 `bid_projects` 增加以下项目级字段：

- `derived_from_project_id`：第一份标书项目 ID；普通项目为空。
- `uniqueness_status`：`none | pending | checking | passed | failed`。
- `uniqueness_result_id`：最近一次与来源项目的查重结果 ID。
- `uniqueness_attempts`：最近一次自动闭环实际执行的改写轮次。
- `uniqueness_auto_run_requested`：仅表示一次全量正文生成已经请求自动衔接查重；用于覆盖进程退出造成的调度间隙，不代表普通 `pending` 都应自动执行。

运行时 migration 与 `sql/workspace_schema.sql` 同步。`BidProject`、preload 类型和 Renderer 类型暴露对应只读字段。

查重详情继续使用现有 `bid_project_duplicate_results` 与 `bid_project_duplicate_matches`，不新增平行结果表。派生关系删除策略沿用项目现有独立生命周期：删除来源项目时不级联删除派生项目，但派生项目将无法再自动查重或导出，并显示来源已不存在。

`derived_from_project_id` 是允许悬空的逻辑引用，不声明数据库外键。删除来源项目时，项目 Store 在同一事务中把其直接派生项目更新为 `status=incomplete`、`uniqueness_status=failed`，清空 `uniqueness_result_id` 并记录“来源项目已删除”；派生项目及其正文仍保留。

每次查重在结果 `summary_json` 中额外保存 `leftContentFingerprint` 与 `rightContentFingerprint`。指纹由去除图片块后的全部正文和稳定节点顺序计算。读取通过状态、显示完成状态和导出前均重新计算两侧指纹；项目关系、任一指纹或零命中结论不一致时，旧结果立即视为失效。

## 派生项目创建

新增 Main 服务负责从来源项目创建差异化项目：

1. 校验来源项目为 `completed` 的普通技术方案，存在招标文件、完整目录和非空正文。
2. 使用来源项目的 source 文件元数据和 `source_group_id` 创建新的 `technical-plan` 项目，并写入 `derived_from_project_id` 与 `uniqueness_status=pending`。
3. 通过 TechnicalPlan Store 的内部快照接口复制招标 Markdown、单文件 Markdown、可用的 Word 原件、标段选择和成功的招标分析结果。
4. 新项目从目录配置/生成阶段开始；不复制目录、全局事实、正文、配图、Agent Session 或任务记录。
5. 任一步骤失败时删除已创建的新项目及项目目录，来源项目保持不变。

项目列表在已完成普通技术方案行提供“再生成一份”命令。创建期间按钮禁用；成功后直接打开新项目。

## 差异化目录

启动派生项目目录生成时，Task Service 从 `derived_from_project_id` 读取来源项目的目录快照，并把它作为 `第一份标书目录.json` 交给目录 Agent。

目录提示增加以下约束：

- 仍以技术评分信息、响应文件要求和用户确认的评分映射为最高优先级。
- 必须重新规划评分项以下的分组、展开路径、叶子拆分和排列方式。
- 不得照搬第一份标书的非固定目录组合、连续标题序列或同级拆分方式。
- 招标文件固定目录、评分项原文标题和必须逐字使用的映射标题允许相同。

最终仍经过现有目录 Schema、评分覆盖、层级和标题审核；差异化要求不得削弱合规覆盖。

## 自动查重改写闭环

新增 `bidProjectVariantDeduplicationService.cjs`，复用 `compareBidContents()`、来源/目标正文节点定位、Tender 段落豁免和现有结构化 AI 改写请求。

正文全量生成所有既有矫正和配图阶段完成并成功落库后，Task Service 自动串行启动 `variant-deduplication` 受管任务：

1. 将状态设为 `checking`，读取来源项目与派生项目的最新叶子正文。
2. 使用 `medium` 灵敏度和两侧招标原文豁免集合执行查重，保存本轮结果。
3. 若非豁免匹配为零，写入 `passed`、结果 ID 和轮次，查重任务成功并把项目标记为完成。
4. 否则按派生项目正文节点分组，逐段生成改写；来源项目始终只读。
5. 改写前后保留目标段落中的数字、百分比、日期、带书名号的政策/标准名称和关键专名；模型结果为空或保护信息丢失时拒绝落库并重试。
6. 将有效改写写回对应正文节点，再从头执行完整查重。
7. 最多执行 5 轮。第 5 轮后仍有命中时写入 `failed`，保存最终结果并使查重任务失败；已经成功落库的正文任务保持成功。

每一轮都基于已经落库的最新正文重新定位，避免多轮修改使用过期段落索引。单轮内同一正文节点的多段修改合并后一次保存，避免相互覆盖。

任务日志展示当前查重轮次、待改写重复组数量、已改写数量和复检结果。页面卸载不取消该任务；任务使用自身的技术方案互斥锁、AI 队列作用域和取消信号。

首次自动检查和后续人工重试使用同一个 `variant-deduplication` 受管任务。它写入 TechnicalPlan Store 的 `variantDeduplicationTask`，使用技术方案项目级互斥、AI 队列作用域、取消信号和任务事件。派生项目开始全量正文生成时持久化 `uniqueness_auto_run_requested=1`；正文成功并释放当前项目任务锁后 Task Service 自动启动查重，并在成功取得查重任务后清除该标记。项目列表为 `pending` 或 `failed` 且仍有完整正文的派生项目显示“重新查重”命令，不重新生成正文。

正文任务成功与自动查重任务启动之间如果发生应用退出，启动恢复只扫描“正文任务成功 + 派生项目 + `uniqueness_auto_run_requested=1`”的项目并自动补启动查重任务。正文任务失败或取消时清除该标记；手工正文修改与用户主动取消查重同样清除该标记并回到普通 `pending`，后续只由“重新查重”入口触发。查重任务执行中被应用退出打断时按现有不可恢复任务规则转为 error，并保留最近一次已落库正文和查重结果，用户可点击“重新查重”。

## 状态失效与导出

TechnicalPlan Store 在正文发生实际修改时调用项目级变更回调，在同一条项目更新中将派生项目改为 `status=incomplete`、`uniqueness_status=pending` 并清空结果引用。自动查重期间的每次落库也会先形成 `pending`，最终零命中复检再写入 `passed`；因此不会在改写中途留下错误的通过状态。

派生项目状态机如下：

- 创建完成：`status=incomplete`、`uniqueness_status=pending`。
- 目录、事实或正文任务运行：`status=generating`；正文修改保持或重置 `uniqueness_status=pending`。
- 正文任务成功、自动查重尚未启动：`status=incomplete`、`uniqueness_status=pending`、`uniqueness_auto_run_requested=1`；Task Service 随即自动启动查重，应用启动恢复只补调度带此标记的项目。
- 自动/独立查重运行：`status=generating`、`uniqueness_status=checking`。
- 零命中并且两侧指纹已写入结果：`status=completed`、`uniqueness_status=passed`。
- 五轮后仍有命中或查重任务报错：正文任务仍为 `success`，项目为 `status=failed`、`uniqueness_status=failed`。
- 用户取消独立查重：项目回落为 `status=incomplete`、`uniqueness_status=pending`、`uniqueness_auto_run_requested=0`，不得遗留 `checking/generating`，重启后不得自动重跑。
- 通过后的正文修改：原子更新为 `status=incomplete`、`uniqueness_status=pending`，清空结果引用。
- 来源删除或正文指纹不匹配：按失效处理，不允许保持 `completed`。

Task Service 计算派生项目状态时增加门禁：`content-generation` 成功本身只把派生项目写为 `incomplete`，随后自动调度 `variant-deduplication`；只有 `variant-deduplication` 成功且项目 Store 已确认正文任务成功、最新零命中结果与两侧正文指纹一致时才能写为 `completed`。独立重试通过使用同一完成逻辑，因此此前仅由查重失败产生的项目 `failed` 状态可恢复为 `completed`，无需改写已经成功的正文任务记录。

派生项目只有同时满足以下条件才显示为完成并允许导出：

- 正文任务成功；查重失败不得回写或伪造正文任务状态。
- `uniqueness_status=passed`；
- 来源项目仍存在；
- 最近结果的来源、目标项目 ID 与当前派生关系一致，且非豁免命中数为零。
- 最近结果保存的两侧正文指纹与当前两份项目正文指纹一致。

普通项目的完成与导出规则保持不变。

## 错误处理

- 来源项目缺失、未完成或没有正文：拒绝创建并给出中文提示。
- 素材复制失败：回滚新项目，不修改来源项目。
- AI 改写失败或保护信息校验失败：在当前轮内按现有 AI 重试策略重试；最终失败则终止闭环并保留查重结果。
- 达到最大轮次：项目状态为失败，提示仍有多少重复组，可通过“重新查重”再次尝试。
- 用户取消/暂停：沿正文任务作用域传播，不创建脱离管理的独立 AI 请求。
- 独立重新查重失败：保留最近正文和结果，项目保持 `failed`，允许再次执行同一入口。

## 测试与验证

- Store 测试：派生字段持久化、状态失效、同源序号和删除来源后的行为。
- 派生创建测试：只复制招标与分析结果，不复制目录/正文，失败时回滚。
- 目录任务测试：派生项目才注入来源目录文件和差异化规则；普通项目提示不变。
- 自动闭环测试：首轮通过、一次改写后通过、多轮仍失败、保护信息丢失、同一节点多段替换、来源项目不变。
- IPC/Renderer 测试：入口可用条件、创建调用、状态文案和导出阻断。
- 状态机测试：正文任务成功但查重未通过时不能完成，手工编辑原子失效，来源或目标指纹变化后旧结果不能导出，来源删除后派生项目保留但失效。
- 恢复测试：应用在正文成功与自动查重启动之间退出后只按持久调度标记补调度；手工编辑和主动取消不会在重启后自动重跑；查重中断后转为可重试错误。
- Main 导出测试：即使绕过 Renderer 直接调用 IPC，非 `passed`、项目关系不符、指纹不符或非零命中的派生项目均被阻断。
- 定向运行新增/相关 `node --test`，Main 文件执行 `node --check`，然后执行 `npm run smoke:electron-native` 与 `npm run build`。
