# 历史标书适配：一致性检查性能优化设计

日期：2026-10-08
状态：待用户确认

## 目标与结论

缩短反复检查和自动修复后的检查耗时，并让用户看得见当前正在处理的阶段、批次和兼容重试。

直接迁移不代表符合本次招标。直迁章节首次检查仍建立完整事实和语义结果；通过后，正文和相关检查输入不变即可复用。局部改写、定向改写、人工编辑和自动修复均按实际变化失效缓存，与变更事实有关的直迁章节也参加复查。

本次保持现有检查项目、人工事实修正、最多两轮自动修复、导出阻断规则和统计能力。所有缓存和后台状态由 Main/SQLite 管理。

## 已定位的耗时与进度问题

依据当前工作区代码，而不是旧方案中尚未落实的描述：

- 每轮都对全文先提取事实，再对全文做语义检查，两阶段按批串行请求。
- 事实提取示例缺少 `node_id`。多章节响应缺失归属时，整批请求后再逐章请求，最多额外产生一个批次内全部章节数量的请求。
- 当前缓存匹配整份正文和输入，单章变化不能复用其他章节的提取结果。
- 兼容逐章重试期间没有细分进度；自动修复后从 10% 重新开始；运行中的阶段文案被隐藏。
- 既有本地测试采用模拟模型，不能据此估算真实模型耗时或承诺固定提速比例。

## 方案比较

| 方案 | 收益 | 边界 |
| --- | --- | --- |
| 只补 `node_id` 和阶段显示 | 改动小，减少非必要兼容请求 | 单章编辑及修复后仍全文请求 |
| 章节事实缓存＋按真实输入复用语义批次（推荐） | 避免重复提取；相关语义输入不变时复用检查 | 冲突证据变化时保守扩大语义复查范围 |
| 全部跳过直迁章节，只检查改写章节 | 请求最少 | 会遗漏直迁内容与新招标基线、其他章节的冲突，不采用 |

先采用推荐方案。保留当前语义提示词中的全局冲突证据包；不同时引入新的语义裁决算法、模型并发调度或新依赖。严格的按事实关联范围裁剪提示词可以后续单独评估。

## 检查与复用规则

| 触发条件 | 本地预检 | 事实提取 | 语义检查 |
| --- | --- | --- | --- |
| 首次检查，无缓存 | 全部章节 | 全部章节 | 全部章节，包括直迁 |
| 全文和所有输入不变且上次整体成功 | 保持现有整体命中路径 | 复用 | 复用 |
| 改写或人工编辑一个章节 | 全部章节 | 提取变更章，复用其他有效章节 | 复查请求输入变化的批次 |
| 自动修复后 | 全部章节 | 提取修复章，复用其他有效章节 | 同上 |
| 招标基线、全局事实、确认差异变化 | 全部章节 | 当前提取提示词依赖这些输入，缓存失效 | 全部重新检查 |
| 人工事实修正变化 | 全部章节 | 不污染原始候选缓存；若进入提取提示词则失效 | 应用最新修正后按语义输入失效 |
| 章节新增、删除或移动 | 全部章节 | 按章节 ID、正文及路径的真实输入判断复用 | 按新批次的真实输入判断复用 |
| 提取/语义协议升级 | 全部章节 | 对应协议缓存失效 | 对应协议缓存失效 |

“相关输入”包含实际送给模型的招标摘要、全局事实、人工事实、冲突证据和章节路径等，不能只比较正文，也不能直接使用包含全文状态的旧 `inputsHash` 作为章节缓存键。

当前语义请求携带全局冲突证据包。新增、删除、修正或裁决一个冲突会影响所有请求的共享输入，必须全部语义复查。这是本方案保留的保守边界；即使直迁章节正文未变，也不能在共享输入变化时复用其语义结果。

## 缓存与当前运行快照

### 原始事实候选缓存

新增 SQLite 表 `historical_adaptation_content_check_cache`，不复用现有批次审计表作为跨运行缓存。

字段：`project_id`、`phase`（facts/semantic）、`cache_key`、`node_ids_json`、`result_json`、`created_at`、`updated_at`；主键为 `(project_id, phase, cache_key)`。只保存完成结构化归一且归属可靠的响应，不保存错误或未完成响应。无事实但合法的 `candidates: []` 也可缓存。沿用现有项目删除/清空的生命周期清理此表，不增加单独定时任务。

事实缓存按章节保存原始候选及本章有效证据，键由以下真实输入计算：

- 项目和章节 ID、章节路径、正文哈希；
- 提取提示词使用的共享摘要及提取协议版本；
- 若原始多章节提取响应无法可靠拆回章节，则不生成章节缓存，保留现有兼容提取及诊断结果。

缓存候选保留 `kind/slot/qualifier/value/evidence/node_id` 等来源数据，不保存人工覆盖后的值，不把上次全局 `fact_id` 当成此次 ID。在跨章合并之前保留逐章原始值和证据，不能从合并后的 canonical_value 反推原始候选。每次按当前运行的 `inputsHash` 重新归一、合并和生成事实 ID，再应用最新人工覆盖。确定性名称/金额事实仍按当前正文执行。

只对未命中的章节调用模型，继续使用现有字符预算和批次上限。长章节的分片全部成功后才保存章节缓存；失败分片不能形成已完成章。

### 语义批次缓存

语义保持现有批量请求粒度，避免为缓存改成逐章请求而增加首次检查成本。

键按实际语义请求输入计算，包括有序章节及内容、共享摘要、实际截取后的冲突证据包、响应协议和语义提示词版本。不要把运行 ID、批次序号或日志标题等非语义信息放入键。批次成员或其任一输入变化，整个批次重新请求。

凡传入提示词的事实 ID 变化都视为请求输入变化，不以仅替换 ID 的方式复用旧事实裁决。命中缓存后也走现有 findings 归一和 `validateFactResolutions()`，不得绕过基线匹配校验。缓存的是合法模型响应，并非“整体检查通过”凭证；合法的阻断结果可以复用，但仍须阻断并进入当前修复/人工处理流程。

语义缓存的收益会受全局事实 ID、批次重分组和全局冲突证据变化限制。以减少事实提取重复请求为主要稳定收益，不宣称所有未编辑章节都能免除语义调用。

### 当前运行必须完整

复用候选与新提取结果必须重新写入当前 `check_run_id` 的完整批次快照，使用当前正文、输入、协议和事实哈希；缓存命中也计入当前运行覆盖。

保持 `getHistoricalAdaptationContentFacts()` 的单次运行完整性约束：预期节点完整覆盖、所有批次成功、索引连续、指纹匹配。不能把旧 run 的若干批次直接拼接成当前有效事实快照。整体成功还必须完成本地预检和全部语义批次。

已有 stale 行为只使整体快照过期，保留按真实键匹配的独立缓存。中断任务已有的有效缓存可供重试，但不得使失败运行被判定完成。修复写入沿用现有原子事务和哈希冲突保护；修复后重新读取 Store 权威正文，重新规划缓存命中范围。

## 减少归属兼容请求

在事实提取提示词的规则和 JSON 示例中明确每条候选必须包含输入中的 `node_id`，并与结构化响应约束保持一致。升级相应提取协议/缓存版本。

保留旧模型缺失归属的兼容逐章重试，未知归属、无效槽位等诊断不降级成“无事实”。每次重试前后更新任务日志和阶段进度，明确显示“第 X/Y 批，归属补提第 M/N 章”。

## 进度与用户可见状态

进度以已完成工作计数，不根据时间伪造百分比。每个批次请求发起前报告当前批次，返回后报告完成批次；命中缓存时报告复用章节/批次数。模型单次请求等待期间允许百分比不变，但必须持续显示当前阶段和批次，不能让用户误以为任务未推进。

预留最多三轮检查和两轮修复的工作区间：

- 本地预检与缓存规划：0–5%。
- 第一轮提取与语义检查：5–60%。
- 第一次修复及第二轮检查：60–80%。
- 第二次修复及第三轮检查：80–99%。
- 成功或终止：100%，同时明确成功/失败状态。

每轮内部按事实、语义、修复阶段完成比例推进。动态出现逐章补提时不回退已报告进度，补提更新计数和文案；后续检查轮次也不回退。不需要额外 IPC 事件或业务状态持久化字段，沿用后台任务 checkpoint、日志及现有 stage。

`AdaptationContentPage.tsx` 在运行时显示当前 stage 和本检查任务最新日志，沿用已有 ProgressBar 和百分比实现。只显示中文阶段、批次和复用数量，不显示缓存哈希或模型协议细节。

## 代码范围

- `historicalAdaptationContentCheckTask.cjs`：提示词、缓存规划与读取/写入、当前 run 快照物化、进度映射；必要的纯缓存键/进度函数抽到同目录专用模块，避免扩大任务文件职责。
- `technicalPlanStore.cjs`：Main 专用缓存读写接口、项目清理、保留既有快照和修复契约。
- `sqliteDatabase.cjs` 与根 `sql/workspace_schema.sql`：新增缓存表和迁移。
- `AdaptationContentPage.tsx`：运行中阶段和任务日志展示。
- 对应任务、Store、数据库迁移和页面测试：覆盖新增行为，保留工作区现有事实修复改动。

不涉及 Analytics、模型并发、导出协议变更、自动改写策略变更或整章重新生成。

## 验收与验证

1. 首次直迁章照常提取/检查；已验证且输入不变时可以复用；改写章与直迁章冲突仍产生阻断。
2. 多章候选带正确 `node_id` 时没有逐章兼容调用；缺归属仍能补提，日志显示补提计数。
3. 改一章或自动修复一章后，未变章节的有效原始提取候选复用；所有当前节点仍形成完整当前运行快照。覆盖全部候选缓存命中、缓存与新提取混合、人工确认的空章等情况。
4. 基线/全局事实/确认差异/路径/协议变化正确失效；人工事实修正不会覆盖原始缓存；删除章不残留到事实表。
5. 全局冲突包或提示词事实 ID 变化时语义缓存失效；不相关输入完全一致的语义批次能够命中。旧 resolutions 不能因缓存绕过基线核验。
6. 失败批次、半个长章、不完整 run、未知归属不能产生可导出的成功检查；缓存失效不破坏事实修正及原子局部修复流程。
7. 所有轮次进度单调不减，运行期间可见阶段与批次；单次模型请求等待时不显示虚构完成量。

运行定向任务/Store/修复/迁移测试及 Electron native 集成测试，对变更的 CommonJS 文件执行 `node --check`，执行 `npm run smoke:electron-native` 和 `npm run build`。通过开发启动手动验证运行阶段、补提、修复复查和页面切换后的后台任务状态。

在模拟模型测试中比较首次、原样复查、单章编辑和单章修复的调用数、复用章节数与检查覆盖，作为优化的可重复证据。真实耗时如需量化，再按用户实际文档与当前模型测量；日志不输出文档正文或密钥。
