# 历史标书适配环节五整体优化设计

## 1. 目标与范围

本设计以用户确认的环节五需求为唯一行为基线，修复当前迁移方案误判、旧项目文字残留、重复点击结果不可信、迁移前后对比失真以及缓存失效边界不清等问题，同时降低大项目迁移时的数据库写入和 AI 调用开销。

环节五继续以历史标书正文为主体，遵循“低扰动迁移”：能可靠定位且没有必须修改证据的章节直接迁移；只有明确受当前招标事实影响的局部内容才自动局部改写；整章定向改写必须由用户主动授权。

本轮范围包括：

- 逐章迁移方案的生成、推荐、人工覆盖和恢复默认。
- 一键建立/更新方案并执行推荐迁移。
- 历史来源定位、局部改写、迁移前后对比和人工正文保护。
- 内容检查、阶段确认、后台任务恢复、缓存版本和增量持久化。
- 当前项目中受旧规则影响的自动结果恢复。

本轮不改变环节一至四的业务目标，不重新设计环节六的审核界面，也不引入自动扩写或自动缩写。环节六只调整与环节五快照、门禁和失效相关的接口。

## 2. 已确认的用户需求

### 2.1 内容迁移

1. 以历史标书正文为主体，大部分章节直接迁移。
2. 不适用于当前招标的服务内容必须删除或重写，不能仅替换项目名称后继续保留。
3. 旧地点、旧行政层级和旧实施对象必须按当前招标资料替换。例如“五峰村”不能残留，且街道项目不能继续使用村级项目表述。
4. 工作量、工期、起止时间、阶段计划和进度节点必须以当前招标基线为准。
5. 用户可逐章选择直接迁移、局部改写或定向改写；人工选择优先于系统推荐。
6. 自动迁移必须克制，不能因为模糊短语命中而把大量章节统一改写。

### 2.2 操作方式

1. “建立/更新迁移方案”是一个用户动作：内部先计算方案，再立即按推荐方式迁移待处理章节。
2. 单章只保留“按此方式迁移本章”：先保存方式，再立即执行；仅切换选项不得修改正文。
3. 删除作用重复、难以理解的迁移入口。批量执行能力由“一键建立/更新”承担，不再单独展示含义重叠的“执行待处理迁移”。
4. 用户可以恢复系统默认推荐；恢复默认只重置人工迁移方式和人工要求，不覆盖人工正文。

### 2.3 对比、确认与保护

1. 页面同时展示格式化后的历史原文和迁移后正文。
2. 历史原文中被删除或替换的文字使用浅红背景；迁移后正文中新增或替换的文字使用浅绿背景；未变化文字不高亮。
3. 直接迁移且内容一致时不显示伪差异；对比必须基于本次迁移实际使用的来源快照和当前迁移结果。
4. 不再逐章确认；全部正文处理完成并通过一致性检查后统一确认环节五。
5. 自动操作不得静默覆盖人工保存正文。覆盖人工正文必须针对当前章节明确确认，取消后不得产生策略或正文写入。
6. 失败必须显示可操作原因，保留完整历史正文，不允许局部应用一半，也不得自动退化为整章重写。

## 3. 当前问题与原设计原因

### 3.1 为什么曾出现大量直接迁移

旧差异记录没有正文影响范围字段。新迁移逻辑只允许结构化范围触发局部改写，因此旧数据全部读取为 `none` 时，大部分章节自然落入直接迁移。后续兼容代码尝试在读取时推断旧差异范围，解决了“全部直接迁移”，却带来了新的过度匹配问题。

保留该原设计中的正确部分：缺少可靠修改证据时必须直接迁移或待人工处理，不能凭猜测调用 AI。需要移除的是每次读取时临时推断旧数据含义的兼容方式。

### 3.2 为什么现在出现大量局部改写

当前规则会从较长历史摘录中提取较宽泛的中文尾部片段，例如“开展农村”“展农村”“村辖区”，再把这些片段作为全局命中词扫描所有章节。通用表述会在大量章节中出现，导致一个差异被关联到许多无关章节，最终把大量章节推荐为局部改写。

这不是缓存显示错误，而是迁移方案本身的关联证据错误。缓存只会让错误方案持续存在。

### 3.3 为什么“五峰村”可能保留

以下任一情况都会导致旧地点残留：

- 章节被错误推荐为直接迁移，正文按原样复制。
- 局部改写没有获得精确旧值，只获得概括性要求。
- 模型返回的 `old_text` 无法在来源正文中唯一命中，任务保留历史正文。
- 重新建立方案复用了旧的成功结果或旧检查快照。
- 一致性检查没有绑定最新正文与规则版本。

因此不能只增加一个字符串替换补丁。必须同时修正规则证据、结果指纹和残留检查。

## 4. 推荐架构

采用“单一用户动作、内部两阶段执行”的结构：

```text
点击建立/更新迁移方案
        |
        v
生成版本化逐章方案（不改正文）
        |
        v
锁定本次目标与来源快照
        |
        v
按推荐/人工方式执行待处理章节
        |
        v
逐章原子提交正文与迁移元数据
        |
        v
确定性章节检查 -> 全量一致性检查 -> 确认本阶段
```

对用户仍是一键操作，对系统则保留清晰的方案边界。这样既满足“点击后直接完成推荐迁移”，又能在任务中断时判断是方案计算失败、某章迁移失败还是检查未完成。

核心组件按职责拆分：

- `historicalAdaptationRuleEngine`：把已确认差异规范化为结构化迁移规则，只负责判断哪些旧值必须改变。
- `historicalSourceIndex`：一次解析历史 Markdown，建立路径感知的章节索引和来源哈希。
- `historicalAdaptationPlanService`：把目录节点、来源索引和规则关联为逐章方案，输出证据，不生成正文。
- `historicalAdaptationMigrationRunner`：执行直接迁移、局部改写和人工定向改写，逐章原子提交。
- `historicalAdaptationComparison`：根据持久化来源快照和当前正文计算展示差异。
- `historicalAdaptationReadiness`：统一计算迁移、检查、终审和导出的门禁状态。

这些职责可以先从现有服务中提取为内部模块，不要求一次性重写整个历史标书适配功能。

## 5. 结构化迁移规则

每条已确认差异生成零到多条正文规则：

```ts
type HistoricalAdaptationRule = {
  id: string;
  differenceId: string;
  scope: 'service-content' | 'location-target' | 'workload' | 'schedule';
  policy: 'must-replace' | 'contextual-review';
  oldValues: string[];
  oldContentEvidence?: string[];
  targetAction: 'replace' | 'remove' | 'rewrite-fragment' | 'review';
  targetRequirement: string;
  evidence: string;
};
```

规则生成要求：

- `oldValues` 必须来自明确的历史项目名称、地点、对象、工作量、日期或完整旧服务事项名称，不允许用任意中文后缀、通用短语或分词残片代替。
- 服务内容差异必须额外保存 `oldContentEvidence`：来自历史招标/标书的完整服务事项标题、完整业务短语或可定位段落摘要。只有差异确认阶段明确认定旧事项应删除或替换时，才生成可自动执行的规则。
- `targetAction` 明确是替换、删除、局部重写还是仅复核。系统不能从自然语言备注中临时猜测动作。
- `targetRequirement` 必须来自当前招标基线或用户确认的差异处理要求。
- `must-replace` 用于能够确定旧值不得保留的事实，例如“五峰村”。
- `contextual-review` 用于语义上可能需要删除或重写、但缺少可安全执行边界的服务内容差异；它只把章节标记为 `review`，不能自动触发 AI。
- 规则没有可靠旧值或目标要求时，不自动局部改写，进入待人工处理。

章节与规则的关联只允许以下证据：

1. 当前章节的来源正文包含完整、规范化后的 `oldValues`。
2. 已确认差异明确绑定到该完整目录路径。
3. 服务内容规则的证据覆盖该章节主题，且命中 `oldContentEvidence` 中的完整服务事项、完整业务短语或唯一段落，不是短后缀。

仅上级目录关联、标题相似、通用词命中或来源摘要中的短片段均不能触发局部改写。

服务内容规则的成功判据按动作确定：`remove` 要求完整旧事项及其明确从属内容不再出现；`replace` 要求旧事项消失且目标事项出现；`rewrite-fragment` 要求只修改被证据定位的段落并满足目标要求；`review` 不自动执行。无法用确定性条件验证成功的服务内容差异必须保留为 `contextual-review`。

## 6. 迁移方式判定

每个叶子章节按以下顺序判定：

1. 无可靠历史来源：推荐为空，状态为 `review`；用户可选择定向改写补充正文或人工编辑。
2. 有人工选择：执行人工选择。
3. 命中一条或多条 `must-replace` 或可验证执行边界的可靠规则：推荐 `local-rewrite`。
4. 只命中 `contextual-review`：推荐为空，状态为 `review`，等待用户定向改写或人工编辑。
5. 有可靠历史来源但没有可靠修改证据：推荐 `direct`。

三种方式的行为：

- `direct`：完整复制已锁定的历史来源正文，不调用 AI。
- `local-rewrite`：只处理该章已关联规则。`replace` 由 Main 根据明确旧值和目标值构造确定性替换，不调用 AI；`remove` 只删除差异确认阶段锁定的证据范围；只有 `rewrite-fragment` 可以调用 AI，且输入和输出都限定在显式授权范围内。所有编辑必须在来源快照中唯一命中，并通过局部性与事实保护校验；应用后还必须通过对应 `must-replace` 或服务内容动作的成功判据；任一校验失败则整章不提交。
- `rewrite`：只有用户选择并填写要求后执行。可结合历史正文、当前招标基线和人工要求整章生成；无历史来源时承担补充生成职责。

局部改写不得修改未关联事实，不得顺带优化表达、扩写、缩写或重排章节。Main 在应用编辑前执行以下确定性局部性校验：

- 每个 edit 的 `old_text` 必须覆盖至少一条关联规则的完整 `oldValues` 或 `oldContentEvidence`，不能只命中相邻通用文字。
- 拒绝以整章原文作为单个 `old_text`，也拒绝编辑覆盖比例超过可配置上限；默认单个 edit 不超过来源正文的 20%，全部 edits 合计不超过 35%。服务内容删除若确需超过上限，必须在差异确认时保存明确的段落范围证据，而不是由模型自行扩大范围。
- 提取并保护未关联的人员数量、设备数量、金额、百分比、日期、项目名称和地点等事实 token；编辑前后这些 token 必须保持一致，只有关联规则明确允许改变的 token 可以变化。
- 编辑不得跨越 Markdown 标题、表格、图片、代码块或 Mermaid 保护边界。
- `replace` 的新文本必须等于旧文本仅把授权旧值替换为目标值后的确定性结果，其他字符序列逐字不变。
- `remove` 的删除范围必须等于预先锁定的证据范围，范围外字符序列逐字不变。
- `rewrite-fragment` 只接收锁定片段，提交后验证片段外正文逐字不变；片段内除目标要求授权的事实和措辞外，受保护 token 及未授权句子保持不变。

任一局部性校验失败都原子回滚、状态转为 `review`，绝不转为整章改写。模型无法稳定返回有效编辑时同样保留来源快照，并展示具体失败类型。

## 7. 一键建立与执行

“建立/更新迁移方案”执行以下事务化编排：

1. 检查招标基线、已处理差异、已确认目录和历史原文是否可用。
2. 取消并等待旧的环节五迁移或检查任务结束。
3. 使用当前版本规则生成新方案和目标集合。
4. 保留人工迁移方式和人工要求；输入指纹兼容时可复用结果，输入不兼容时按失效矩阵处理。stale 的人工 `rewrite` 只保留选择和要求，不进入一键自动目标，必须由用户单章重迁。
5. 始终保留 `content_origin=manual` 的人工正文，并把这类章节从自动目标集合中排除。
6. 对其他待处理章节立即执行推荐或已保留的人工方式。
7. 逐章提交结果和检查状态；个别章节失败不丢失已成功章节。

按钮状态必须区分“正在建立方案”和“正在迁移正文”。任务详情显示总章数、成功数、待人工数、失败数和当前章节。

单章“按此方式迁移本章”遵循相同规则。若当前章是人工正文，先弹出覆盖确认；只有用户确认后才同时保存策略并启动该章迁移。

“恢复默认处理方式”只清除人工选择和人工要求，重新计算推荐，不立即覆盖正文。非人工正文可通过“一键建立/更新”应用新推荐；人工正文仍排除在自动目标外，只能通过单章“按此方式迁移本章”并确认覆盖后应用。人工正文始终保留。

## 8. 历史来源索引与定位

历史 Markdown 导入或内容哈希变化时，先按完整内容哈希保存一份不可变、内容寻址的源版本，再为该版本建立一次章节索引：

```ts
type HistoricalSourceSection = {
  id: string;
  path: string[];
  heading: string;
  level: number;
  occurrence: number;
  startOffset: number;
  endOffset: number;
  contentHash: string;
};
```

目录匹配使用完整路径、标题层级、同名出现序号和内容哈希，不再只取最后一级标题并为每个目标章节重复扫描全文。无法唯一定位时进入 `review`，不得猜测来源。相同历史原文哈希只保存一份不可变源文件，不为每章复制正文。

方案保存来源索引 ID、来源路径和来源内容哈希。执行时若哈希不一致，当前章转为 `stale` 并要求重建方案，不能继续使用旧摘录。

## 9. 真实迁移前后对比

迁移成功时保存本次实际使用的不可变源版本哈希、章节定位信息和 `source_content_hash`。历史原文展示从该内容寻址源版本按需读取，不在每个章节元数据中重复保存完整 `source_excerpt`。

对比规则：

- 左侧历史原文使用 Markdown 格式化展示，被删除或替换的文字加浅红背景。
- 右侧迁移后正文使用 Markdown 格式化展示，新增或替换的文字加浅绿背景。
- 未变化文字保持普通样式。
- 直接迁移且哈希一致时显示“正文未修改”，不产生背景色。
- 对比算法按 Markdown 语义块和文字 token 计算；代码块、Mermaid、图片、表格结构和 HTML 标签作为不可拆分保护块，避免高亮破坏格式。
- 人工编辑后，对比对象仍是最近一次迁移所使用的不可变历史来源快照；页面明确标注正文来源为“人工修改”。

对比结果仅在 Renderer 按需计算，不作为第二份权威正文持久化。内容寻址源版本属于导入源档案，不是平行业务正文；只有源档案缺失或校验失败时，页面才标记“来源快照不可用”，不展示可能失真的高亮。

## 10. 持久化与版本

SQLite 继续是结构化业务状态的唯一权威，正文继续保存在 `technical_plan_outline_nodes.content`。

新增版本与指纹：

- `difference_schema_version`：差异及正文影响范围的数据版本。
- `rule_engine_version`：规则生成算法版本。
- `content_plan_version`：逐章迁移方案结构版本。
- `plan_inputs_hash`：目录、差异、招标基线、历史来源索引和规则版本的组合哈希。
- `migration_output_hash`：该章来源、规则、方式、人工要求和结果的组合哈希。
- `checked_content_hash`、`checked_inputs_hash`：一致性检查快照。

旧数据通过一次性 SQLite migration 持久升级。旧差异范围根据可证明的完整字段迁移；无法证明的范围写为 `none` 并等待用户确认，不再在每次读取时动态猜测。

逐章方案从项目级大 JSON 迁移到独立 SQLite 表，至少包含项目 ID、节点 ID、推荐方式、人工方式、人工要求、来源定位器、各类哈希、状态、正文来源、关联规则、错误信息和更新时间。SQLite migration 在同一事务内完成建表、旧 JSON 导入和项目级 `content_items_storage_version` 标记；任一步失败则整笔回滚。标记完成后新表是唯一权威，Store 不再读取或写入旧 JSON；新表与旧 JSON 同时存在时也始终以已完成版本标记和新表为准，防止重启后重复导入旧策略。旧 JSON 只作为兼容备份保留到后续独立清理版本。

## 11. 增量事件与性能

当前每章 checkpoint 重写完整内容项 JSON，并把完整数组和目录状态推送给 Renderer，在章节多、来源摘录长时会放大序列化、SQLite 写入和 React 合并成本。

优化后：

- 每章只更新自己的方案行和对应正文节点。
- 任务事件发送 `contentItemPatch`、`outlineContentPatch` 和汇总计数，不发送完整内容项数组或完整目录。
- Renderer 收到 patch 后按节点 ID 合并；重新进入页面时再从 SQLite 读取权威快照。
- 历史来源正文按选中章节读取，不随项目状态全量传输。
- 迁移任务保持有限并发或串行写入，确保同一项目 checkpoint 顺序稳定；AI 请求继续走现有统一队列。

方案生成复杂度从“目标章节数 × 历史全文扫描”降为“一次索引 + 逐章索引查询”。

## 12. 缓存和失效规则

缓存复用必须同时满足版本和输入指纹一致，不能只依据章节状态为 `success`。

- 仅重新打开页面：不失效任何业务数据。
- 仅修改 UI 选择但未执行：不写持久状态，不失效正文。
- 保存迁移方式或人工要求：只使当前章迁移结果 stale，并使全量检查、阶段确认和终审 stale。
- 保存人工正文：只更新当前章正文、来源和确定性检查；全量检查、阶段确认和终审 stale。
- 修改差异：只失效受该差异规则影响的自动章节；无法可靠计算影响范围时才全量失效。
- 修改目录：沿用 `saveOutline(reason)` 协议，保留可重映射章节，失效新增、删除、改名或来源映射变化的章节。
- 修改招标基线或历史源文件：失效相关方案与自动结果；人工正文保留但检查 stale。
- `rule_engine_version` 或 `content_plan_version` 变化：自动结果失效，人工正文保留。
- 检查哈希不匹配：检查结果不可用于阶段确认、终审或导出。

Renderer 不实现第二套失效规则。所有失效和门禁由 Main Store/Service 统一处理。

人工选择和既有成功结果按以下矩阵处理：

| 既有方式 / 正文来源 | 相关输入或规则未变化 | 相关输入或规则变化 |
|---|---|---|
| 人工 `direct`，正文非 `manual` | 保留选择和结果 | 保留选择；来源仍相同可保留正文但检查 stale，来源变化则结果 stale 并需重迁 |
| 人工 `local-rewrite`，正文非 `manual` | 保留选择和结果 | 保留选择，结果 stale，必须按新规则重迁 |
| 人工 `rewrite`，正文非 `manual` | 保留选择、要求和结果 | 保留选择和要求，结果 stale，必须由用户单章重迁；不进入自动批量目标 |
| 任意方式，正文为 `manual` | 保留全部正文 | 保留全部正文，检查 stale；只能单章确认覆盖 |

输入指纹不兼容时可保留人工意图，但不能把旧成功结果继续当作有效结果。

## 13. 一致性检查与统一门禁

检查分为确定性预检和语义检查：

1. 确定性预检覆盖旧值残留、空正文、占位符、迁移失败、未处理 review、来源或方案 stale。
2. 确定性预检存在阻断时，直接返回 findings，不调用 AI。
3. 预检通过后，再按内容哈希和输入哈希复用或批量执行语义检查，覆盖工作量、工期进度、服务内容和跨章节冲突。

“五峰村”等 `must-replace` 旧值属于确定性阻断，不能在环节五或环节六通过备注、已处理状态或人工豁免绕过。确需保留时必须回到差异确认阶段修改规则并生成新快照；在规则仍为 `must-replace` 时，阶段确认、终审和导出始终阻断。

Main 提供统一的 `getHistoricalAdaptationReadiness()`，供环节五确认、环节六审核和导出复用。返回至少包含：

```ts
{
  ready: boolean;
  blockingCount: number;
  firstNodeId?: string;
  findings: Finding[];
  planInputsHash: string;
  contentHash: string;
  checkSnapshotValid: boolean;
}
```

环节五确认条件：所有叶子有可执行且成功的结果、正文非空、无活动任务、方案和来源未 stale、最新检查成功且无 blocker。环节六和导出不得各自复制一套不同判断。

## 14. 后台任务恢复与错误展示

任务持久化本次方案 ID、目标节点集合、已完成节点和当前阶段。应用重启后：

- 已成功且输出指纹有效的章节保持成功。
- 当时处于运行中的章节转为可重试错误。
- 未开始章节保持待处理。
- 人工正文不进入自动恢复目标。
- 检查任务中断后状态为 error，旧检查快照不可作为有效门禁。

页面提供“重试未完成章节”，复用原 `plan_id`。目标只允许该计划中已有可执行 `local-rewrite`，且失败类型为模型临时错误、`invalid-edit-structure`、`old-text-not-found`、`old-text-ambiguous` 或 `no-effective-change` 的节点，以及尚未开始但已有自动推荐方式的节点；`success`、`contextual-review`、无 mode、人工 `rewrite`、人工正文、`source-stale`、`non-local-edit`、`protected-fact-changed` 和 `residual-old-value` 均不自动重试。重试前逐章重新校验计划版本、来源哈希、规则哈希和既有输出指纹：仍一致才执行，不一致则转为 `stale` 并要求重新建立方案。“重新建立/更新迁移方案”会生成新计划并重新计算目标，与重试旧计划严格区分。重复提交同一重试命令按 `plan_id + node_id + output_fingerprint` 幂等处理。

局部改写错误分类至少包括：

- `invalid-edit-structure`：模型未返回有效编辑数组。
- `old-text-not-found`：原文片段未命中。
- `old-text-ambiguous`：原文片段存在多个命中。
- `no-effective-change`：新旧文本相同或应用后内容未变化。
- `residual-old-value`：应用后仍存在必须删除的旧值。
- `source-stale`：执行时来源哈希已经变化。
- `non-local-edit`：编辑范围过大、跨越保护边界或没有覆盖关联规则证据。
- `protected-fact-changed`：未获规则授权的人员、设备、金额、日期或地点事实发生变化。

界面显示中文原因和可执行建议：重试局部改写、改为定向改写、人工编辑或重建方案。错误详情可写入开发者日志，但日志失败不得影响正文保留。

## 15. 当前项目恢复策略

部署新规则后，对当前项目执行一次受控恢复：

1. 取消并等待当前错误的迁移或检查任务结束。
2. 备份当前项目数据库状态。
3. 保留所有 `content_origin=manual` 正文及其节点映射。
4. 将旧规则生成且输入指纹不兼容的自动结果标记为 stale，不直接删除正文。
5. 使用新规则生成方案预览和统计，确认直接迁移、局部改写、待人工处理的分布合理。
6. 执行非人工章节迁移。
7. 运行确定性检查，重点确认“五峰村”、旧行政层级、工作量和日期残留为零。
8. 运行语义一致性检查，通过后再开放阶段确认。

若新方案统计异常，任务在执行正文前自动阻断并提示检查规则，避免再次批量写入错误结果。默认阈值为：使用低置信或上下文证据的单条规则命中超过全部可靠来源章节的 30%，或这类规则造成的 `local-rewrite` 超过可靠来源章节的 50%。精确完整旧值驱动的全局 `must-replace` 不受覆盖率阈值阻断，即使“五峰村”真实出现在多数章节也必须全部处理；系统改为展示命中预览和数量。阈值命中只阻断低置信规则的自动执行，必须回到差异规则修正后重建方案。

## 16. 分批实施

### 第一批：正确性与用户行为

- 移除宽泛中文尾部片段匹配，落地结构化规则和精确章节证据。
- 修复三种迁移方式判定和“五峰村”等旧值残留门禁。
- 保持“一键建立/更新并执行推荐迁移”。
- 完成历史来源可靠定位和真实红绿对比。
- 统一单章操作、恢复默认和人工正文覆盖保护。

### 第二批：持久化、缓存与性能

- 引入版本和输入指纹，完成旧数据一次性迁移。
- 建立历史 Markdown 索引和逐章迁移方案表。
- 改为逐章 checkpoint、增量事件和按需来源读取。
- 完成后台任务重启恢复。

### 第三批：检查、审核与门禁

- 确定性预检优先，语义检查按哈希缓存和批量执行。
- Main 侧集中 readiness。
- 环节六审核结果绑定快照，保留未变化 finding 的处理结果。
- 区分必须修复与建议性/contextual finding 的人工豁免，并统一确认、终审和导出门禁；`must-replace` 永远不得豁免。

每批都必须保持数据库可升级和现有项目可继续打开。第一批完成后即可修复当前迁移错误；第二、三批不得改变第一批确认的用户操作语义。

## 17. 验收标准

### 17.1 规则正确性

- 包含“五峰村”的来源章节均被可靠识别；迁移后正文的阻断残留为零。
- 通用短语不会导致无关章节进入局部改写。
- 有可靠来源且无修改证据的章节全部直接迁移。
- 服务内容删除/重写、工作量和工期规则只影响有明确证据的章节。
- 局部编辑任一项失败时，该章一个编辑也不提交。
- 局部改写不能通过“整章旧文到整章新文”的单个 edit 绕过约束，未授权事实 token 不发生变化。
- 明确 `replace` 除目标旧值外逐字不变，`remove` 只能删除锁定范围；即使编辑范围较小，任何无关措辞润色也会被拒绝。

### 17.2 用户操作

- 点击“建立/更新迁移方案”一次即可完成方案计算和推荐迁移。
- 单章选择方式后只需点击一次即可执行。
- 没有含义重复的批量迁移按钮。
- 恢复默认不会覆盖人工正文。
- 不存在逐章确认入口，完成检查后统一确认环节五。

### 17.3 对比显示

- 左侧真实来源与右侧当前正文均正确渲染 Markdown。
- 删除/替换前文字浅红，新增/替换后文字浅绿。
- 未变化文字和完全直接迁移章节不高亮。
- 图片、表格、代码块和 Mermaid 不因差异标记而损坏。

### 17.4 缓存与恢复

- 输入和版本未变化时复用方案、迁移结果和检查结果。
- 任一相关输入变化时只复用指纹仍有效的数据。
- 重启客户端后已完成章节不重复执行，运行中章节可明确重试。
- 所有人工正文均在更新方案、规则升级和任务恢复后保持不变。

### 17.5 性能

- 历史全文只解析一次，不按章节重复扫描。
- 单章 checkpoint 不重写完整内容项数组或发送完整目录。
- 确定性阻断存在时不调用语义检查模型。
- 固定 100 章、约 120,000 字符历史原文夹具中，每个 checkpoint 事件的序列化负载不超过 64 KiB，且不包含完整目录或完整内容项数组；一次冷缓存方案生成只解析历史全文一次，索引查询次数与章节数线性相关，不再按章节全文扫描。Renderer 使用同一固定夹具连续接收 100 个模拟 patch，在发布构建、空闲主线程条件下记录 95 百分位合并耗时不超过 16 ms。

## 18. 验证计划

- 规则单元测试：旧值规范化、精确命中、通用短语拒绝、服务内容规则和多规则关联。建立固定真值夹具，明确包含“五峰村”的预期节点集合、只包含“开展农村”“展农村”“村辖区”的非命中节点集合和每个节点的预期 mode，断言无额外 `local-rewrite`。
- 迁移单元测试：直接迁移、确定性 replace、锁定范围 remove、局部编辑原子性、整章 edit 拒绝、编辑比例上限、小范围无关措辞改写拒绝、未授权事实保护、残留阻断、人工定向改写和人工正文保护。
- Store/migration 测试：版本升级、逐章表、输入指纹、局部失效、任务恢复和增量 checkpoint。
- 对比测试：插入、删除、替换、中文标点、Markdown 表格、图片、代码块和 Mermaid。
- 流程测试：一键建立并迁移、单章迁移、恢复默认、检查、统一确认、终审和导出门禁。
- 真实项目回归：保存经人工核对的节点期望清单，逐节点断言推荐方式；检查所有“五峰村”预期命中节点及迁移后残留为零，断言三类通用短语节点不误命中，并验证人工正文哈希完全不变。
- 工程验证：相关 `node --test`、修改 `.cjs` 的 `node --check`、`npm run smoke:electron-native`、`npm run build`，并启动 Electron 完成桌面与窄屏手工验证。

## 19. 与旧规格的关系

本文取代 `2026-10-01-historical-bid-adaptation-content-design.md` 中以下已不符合最新确认的行为：

- “建立方案不生成正文、再由用户单独启动批量迁移”改为“一个用户动作，内部先建方案再执行推荐迁移”。
- 基于宽泛差异片段自动关联章节的方式改为结构化旧值和完整证据关联。
- 每章重复保存完整来源摘录改为来源索引和按需读取。
- 项目级大 JSON 的高频整体写入改为逐章表和增量事件。

旧规格中仍然有效的低扰动迁移、三种人工可选方式、无逐章确认、人工正文保护、原子局部编辑和一致性检查要求继续保留。
