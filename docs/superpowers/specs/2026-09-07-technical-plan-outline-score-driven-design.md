# 技术方案目录按评分标准驱动生成设计

## 背景

当前技术方案目录生成 V2 会先根据全文字数和单节字数推算 `ai-generate` 叶子目标，再把目标数量分配给技术分支。完整目录生成后，如果实际叶子数不等于目标，还会要求用户选择接受、自动调整或自定义调整。

这种流程会让数量目标反向影响目录结构。Agent 可能为了接近目标数量而合并、概括、过度拆分或补充目录，导致招标评分标准中的具体要求不能稳定、完整地体现在目录中。例如评分原文明确包含“建设目标”，生成结果可能只保留“技术路线、实现方法、关键技术”。

本设计把目录生成的第一约束改为评分标准覆盖和专业结构。字数推算值继续保留，但只作为正文容量参考，不再作为目录必须精确达到的叶子数量。

## 目标

1. 用户确认一级目录后，以技术评分标准决定该一级目录下的必要结构。
2. 保留评分表的分组、评分行、原始顺序和有业务含义的限定词。
3. 允许删除评分话术，但不允许随意概括、改写、合并或遗漏评分要求。
4. 下级目录按独立写作单元适度拆解，不按标点机械拆分，也不过度细化。
5. 允许少量、有明确价值的专业结构补充，但补充项不能替代评分原文要求。
6. 字数推算值只提供容量参考，不触发凑数、重复询问或流程阻断。
7. 目录最多七级；越往下标题和说明必须越具体。
8. 最终审核能够验证每条评分要求在目录标题或节点说明中得到承接。
9. 目录生成后的 AI 调整仍然保持评分覆盖和标题保真。
10. 七级目录能够正常进入正文生成、图片规划和 Word 导出。

## 非目标

1. 不修改一级目录人工确认流程。
2. 不改变目录节点在 SQLite 中的权威存储方式。
3. 不改变叶子的 `ai-generate`、`template-fill`、`point-to-point`、`other` 内容处理模式。
4. 不要求所有目录达到七级，也不为达到层级上限制造目录。
5. 不要求把评分原文中的每个逗号、顿号或评价词都变成独立目录。
6. 不修改正文生成的全文字数和强控单节字数能力。
7. 不修改 Analytics、IPC、preload 或数据库 schema。

## 已确认的业务原则

### 评分要求优先级

目录结构按以下优先级生成：

1. 评分原文明确要求的响应内容。
2. 为形成完整、可编写结构而增加的受控专业补充。
3. 根据材料复杂度进行的必要下钻。
4. 字数推算值提供的容量参考。

较低优先级不得删除、合并或弱化较高优先级内容。

### 一级目录

一级目录以用户确认结果为准。除非评分规划阶段得到用户明确批准，否则后续阶段不得新增、删除、合并、改名或调整一级目录顺序。

### 评分映射节点

评分表左侧合并单元格通常表示评分大项；用户确认的一级目录可直接对应该评分大项。右侧每条独立评分行作为该一级目录下的评分映射节点，并保持原始顺序。

评分映射节点标题尽量保留招标原文，只允许删除不影响业务含义的评分外壳：

- 可删除开头的“根据投标人针对”“根据投标人对”“依据投标人提供的”等评分主语和引导语。
- 可删除结尾的“进行打分”“根据描述评分”“得 0 至 5 分”等评分动作和分值枚举。
- 可在不改变含义时删除重复的“本项目”或补足共享谓语，使标题成为自然、可用的目录名称。
- 不得删除“项目实施过程中”“服务需求中”等具有业务范围含义的限定词。
- 不得使用更短但改变范围的概括标题替代评分原文。

例如：

- “对本项目的理解：政策背景、项目技术要求理解进行打分”可规范为“项目的理解”。
- “根据投标人对本项目实施过程中的重点、难点问题分析及解决措施……进行打分”应保留为“项目实施过程中的重点、难点问题分析及解决措施”，不得概括为“项目重点难点分析及解决措施”。

### 评价维度

“全面性、合理性、科学性、先进性、可行性、扩展性、安全性、独特性”等用于评价质量的词不生成独立目录。它们写入对应评分映射节点的 `description`，作为正文生成和最终审核约束。

评分标准中的范围、对象、过程和交付要求也可由“标题 + description”共同承接，但不得只写成没有具体信息的泛化说明。

### 适度拆解

评分映射节点的下一级按可独立编写的专业主题拆解：

- 不按逗号、顿号、冒号机械拆分。
- 具有独立响应价值的不同对象可以拆分。
- 构成完整响应闭环的动作应保持在同一目录中。例如“重点问题分析及解决措施”不拆成孤立的“重点问题分析”和“解决措施”。
- “制度及保证措施”“方案及措施”“计划及保证措施”等并列结构，如果两部分各自具有充足、独立的写作内容，可以拆成不同目录。
- 父目录已明确业务对象时，子目录可以省略重复语境。例如在“项目档案归档、数据保密制度及保证措施”下使用“数据保密制度”和“保证措施”。子节点 `description` 仍须说明“保证措施”指数据保密保证措施。
- 只有一个自然写作单元时，当前节点保持叶子，不创建只有一个子节点的冗余层级。

### 受控专业补充

允许增加评分原文未直接列出、但对形成完整技术方案确有必要的目录：

- 总体方案、总体设计、系统设计或整体规划类评分节点只列局部要素、缺少统领性介绍时，可以增加一个总体介绍节点。信息化、软件、平台类项目可使用“总体架构设计”；其他项目应优先使用招标原文中的相近表述或“总体设计思路”。
- 问题分析类评分节点可以增加“其他具体问题分析与应对”“合理化建议”等具有明确写作价值的节点。
- 同一个评分映射节点最多增加一个同类总体介绍节点。
- 补充节点必须有明确对象和写作任务，不能使用“其他内容”“相关说明”“方案概述”等空泛标题。
- 补充节点不得替代、合并或改变评分原文明确要求的节点。
- 补充节点应在内部评分规划中标记为专业补充，最终正式目录不展示内部来源标记。

## 目录深度和质量

### 七级上限

目录允许一级至七级。七级是上限，不是目标。

只有同时满足以下条件才允许继续下钻：

1. 当前主题确实包含至少两个不同的下级写作单元。
2. 每个子节点都能缩小父节点范围、明确响应对象、落实具体过程或形成具体交付内容。
3. 每个子节点都能独立形成非重复正文。
4. 拆分依据来自评分原文、招标技术要求、用户确认信息、原方案或可信参考材料。

不得继续下钻的情况：

- 只能把父标题换一种说法。
- 只能增加“概述、总体说明、具体内容、相关要求”等空泛节点。
- 子节点之间语义重复或正文范围无法区分。
- 只有一个子节点。
- 拆分后超出七级。

### 标题递进

子节点标题必须比父节点更具体。具体化方式包括：

- 从总体对象缩小到组成部分。
- 从方案缩小到具体阶段、流程、方法或措施。
- 从问题集合缩小到明确的问题类型和响应闭环。
- 从制度体系缩小到具体制度或保证措施。

标题只写目录名称，不包含章节编号、Markdown 标记、评分分值或“进行打分”等话术。

### description 质量

每个节点的 `description` 必须至少明确以下一项实际信息：

- 本节点需要响应的招标要求或评分要求。
- 需要阐述的对象、范围、过程、方法、措施或交付物。
- 适用于本节点的全面性、合理性、科学性等评价维度。
- 与父节点和同级节点的内容边界。

禁止使用下列类型的空洞说明：

- “详细介绍本节相关内容。”
- “根据招标要求进行阐述。”
- “说明本方案的具体情况。”
- 仅重复标题且没有增加对象、范围或写作要求。

最终审核应把空洞 description 归入 `professional-structure` 问题。

## 字数推算值

### 保留现有推算

现有全文最少字数、最多字数和每小节字数仍可推算建议叶子容量。推算值保留在任务统计中，用于向 Agent 描述正文容量，不再作为必须精确达到的结构目标。

### 新语义

- 先完成评分必备节点和受控专业补充，再统计自然形成的 `ai-generate` 叶子数。
- 推算容量小于自然叶子数时，保留全部自然叶子，不合并、不删除、不报错，也不阻止进入下一步。
- 推算容量大于自然叶子数时，只有存在真实、可独立编写的内容时才继续下钻；不得为消耗容量补充重复、近义或空泛目录。
- 实际叶子数与推算值不一致时，不调用叶子数量差异询问，不要求反复调整。
- 最终审核不再使用精确目标或正负二范围判断目录是否合格。
- 前端不再把叶子数量与字数推算不一致显示为目录异常或阻止用户继续。
- 全文字数和强控单节字数仍在正文生成阶段生效。

### 需要移除的旧规则

1. 多技术分支按固定总数分配叶子。
2. 普通技术分支必须分配至少两个叶子。
3. 实际叶子数不等于目标时固定询问用户。
4. 用户选择调整后仍不精确时再次询问。
5. 最终审核要求叶子数位于目标正负二范围。
6. 因叶子数量不符合字数范围而阻止进入后续步骤。

“父节点一旦展开必须至少有两个子节点”属于结构质量规则，继续保留；它不等于“每个技术分支必须展开成至少两个叶子”。

## 中间数据设计

当前 `technical-score-groups.json` 只保存评分大项的 `title`、`description` 和自由文本 `detail_points`，不足以机械检查评分行和响应要点是否被覆盖。

评分规划中间数据需要表达以下信息：

- 评分大项及其原文和顺序。
- 每条独立评分行的原文、规范化目录标题和顺序。
- 评分行中明确要求响应的内容实体。
- 评价维度。
- 允许的专业补充项及理由。
- 每个评分行和响应内容实体对应的预期目录路径或稳定内部标识。

推荐逻辑结构如下，具体字段名在实施计划中确定：

```json
{
  "groups": [
    {
      "requirement_id": "R1",
      "source_title": "项目总体方案",
      "target_title": "项目总体方案",
      "criteria": [
        {
          "criterion_id": "R1-C1",
          "source_text": "对本项目的理解：政策背景、项目技术要求理解进行打分……",
          "target_title": "项目的理解",
          "response_points": ["政策背景", "项目技术要求理解"],
          "evaluation_dimensions": []
        }
      ]
    }
  ]
}
```

正式目录节点仍只保存现有业务字段。评分来源、内部标识和覆盖关系保留在 Agent 任务工作区，不写入最终 `outlineData`。

## 生成流程

### 工作流适用边界

- 普通技术方案和完整响应文件模式：用户确认一级目录后，新规则完整应用于 `attr=技术` 且需要 AI 正文的技术分支。商务、资信、模板填充、点对点应答和其他特殊处理分支保持一级目录确认时的处理方式，不按技术评分标准扩展。
- 技术文件独立成册模式：一级目录直接对应评分大项，评分表右侧独立评分行和明确响应内容从二级开始生成，不在根节点下重复生成同名评分大项。
- 已有方案扩写的“AI 补充”模式：评分标准决定必要覆盖，原方案用于保留已有专业结构和生成更下级目录；评分原文缺失内容必须补齐，意思相近但已经完整覆盖的内容不重复添加。
- 已有方案扩写的“仅使用原方案目录”模式：原方案目录结构优先，不因新规则重排或概括原方案节点；技术评分信息只用于检查并补充原方案语义上确实缺失的技术要求。新增补充仍须位于用户确认的一级目录下，并遵守评分标题保真、适度拆解和七级上限。

所有模式都使用新的 description 质量规则和七级上限。字数推算值在所有模式中都只作容量参考。

### 1. 技术评分信息提取

上游分析保留评分表的合并单元格关系、每条评分行、完整评分标准、原始顺序、分值和来源位置。不得在这一阶段提前合并相近评分行或把多条评分标准概括成一段摘要。

### 2. 一级目录生成与确认

保留现有流程。Agent 生成一级目录，用户确认需要继续使用的一级目录和内容处理模式。

### 3. 评分结构化与目录规划

Agent 把技术评分信息转换为结构化评分组和评分行，识别：

- 评分原文核心标题。
- 可删除的评分外壳。
- 明确响应内容。
- 评价维度。
- 允许的受控专业补充。

保留现有评分规划确认：同级评分大项的合并、拆分、遗漏、新增、目标层级变化或一级目录变化仍需用户批准。评分映射节点以下的适度拆解和受控专业补充不作为同级评分规划变化。

### 4. 完整目录生成

Agent 先生成评分映射节点，再生成明确响应内容，最后按专业结构决定是否增加受控补充或继续下钻。字数推算值仅作为容量参考。

生成必须遵守：

- 原文要求先覆盖，补充结构后生成。
- 保持评分行和明确响应内容的顺序。
- 不因相近而合并来自不同评分行的节点。
- 不因字数容量不足删除要求。
- 不因字数容量富余增加空泛节点。
- 父节点至少两个子节点。
- 最多七级。

### 5. 确定性覆盖检查

宿主程序根据结构化评分规划生成覆盖上下文，至少检查：

- 每条评分行是否有对应评分映射节点。
- 每个明确响应内容是否出现在预期节点标题、子目录标题或相关节点 description 中。
- 映射节点是否位于正确一级分支和规划层级。
- 是否保持来源顺序。
- 是否存在超过七级、单子节点或非法内容模式。
- description 是否为空或只有泛化套话。

覆盖检查不再判断叶子数是否等于字数推算值。

### 6. Agent 最终审核

Agent 使用宿主程序检查结果和评分原文，补充语义审核：

- 评分语义是否完整。
- 标题是否改变原文范围。
- 下级拆解是否过细或过粗。
- 补充节点是否确有专业价值。
- 同级节点是否重叠。
- 标题和 description 是否具体。

评分来源节点不得静默改名、合并或删除。发现评分覆盖缺失、评分标题变义或需要结构重排时，必须集中向用户确认。只有不涉及评分来源节点的补充节点文案优化和明显空洞说明修复可以静默完成。

### 7. 保存

继续统一编号并移除内部 `branch_id` 等 Agent 工作字段。正式目录和字数控制快照按现有方式写入 SQLite，后续正文生成状态按现有规则失效。

## AI 调整目录

目录生成后的 AI 调整复用同一持久 Agent 工作区。调整前覆盖写入用户当前最新目录，但继续读取结构化评分规划和评分原文。

调整要求：

- 与用户要求无关的目录保持不变。
- 不得删除、合并或改写评分来源节点，除非用户明确要求且确认影响。
- 调整后重新执行评分覆盖、七级上限、父节点数量和 description 质量检查。
- 新增节点继续遵守适度拆解和受控补充规则。

## 七级目录联动

### 目录生成和调整

目录 JSON Schema、评分目标层级上限、宿主结构审核以及生成和调整 Prompt 的最大层级统一从六级改为七级。

### Markdown 中间材料

Markdown 原生只支持六级标题。正文审核、图片规划等中间材料继续把第七级以六级 Markdown 标题承载，但必须保留完整目录 ID，例如 `1.2.3.4.5.6.1`，以 ID 区分真实层级。

### Word 导出

Word 导出当前只配置六套标题样式。第七级目录沿用第六级标题的字体、字号、段落、边框和编号样式，不新增第七套用户配置。

第七级必须保留完整七级编号，不能被截断为六级编号。原生多级列表最多仍使用现有六级配置；第七级使用沿用六级视觉样式的显式编号文本，避免与第六级编号冲突。

导出格式页面继续只展示六级标题样式，文案补充说明“七级及更深兼容目录沿用六级样式”；由于目录生成上限为七级，实际只涉及第七级。

### 其他消费者

正文生成、图片规划和目录查重中对 Markdown 标题级别的六级截断可保留，但必须确认其目录 ID 和父子树没有被截断。目录查重若使用 `level` 判断路径，应能区分真实七级节点，不能把七级节点错误视为六级同级节点。

## 前端行为

目录生成配置继续提供全文最少字数、最多字数、每小节字数和强控小节字数。

帮助文案明确说明：

> 字数设置用于正文容量和小节篇幅控制，不用于强制拆分、合并或凑齐目录数量。

删除目录完成后的“AI 生成小节数量未达到预期”异常弹窗，以及从目录步骤进入全局事实步骤时基于叶子数量范围的阻止逻辑。字数控制快照仍必须存在，因为正文生成继续使用它。

正文生成阶段的全文字数和单节字数警告保持不变。

## 兼容性和恢复

- 现有已生成目录无需迁移，重新生成后才使用新规则。
- 正式 `outlineData` 字段不变，因此 SQLite schema、IPC 和 preload 不变。
- 目录生成一级目录确认阶段的恢复方式不变。
- 旧持久 Agent Session 由重新生成目录时的现有清理流程删除，不需要兼容旧中间文件 schema。
- 目录调整只能在同一轮新规则生成的持久工作区中获得完整评分映射；旧目录的调整继续使用现有目录作为输入，但无法获得新增的确定性来源覆盖检查，应提示重新生成目录后再使用完整保护能力。

## 错误处理

- 无法从技术评分信息中识别有效评分行时，沿用 `report-failure`，要求用户补充或重新解析评分信息，不编造评分项。
- 评分原文存在结构歧义且不同解释会实质改变目录时，集中调用一次 `ask-user`。
- 字数推算值与自然叶子数不一致不是错误，不调用 `ask-user`。
- 七级以内无法在不遗漏评分要求的情况下形成合法结构时，向用户说明具体冲突，不通过重复、空泛目录规避。
- Word 导出第七级样式兼容失败时应明确报错，不静默丢失标题或编号。

## 验收标准

1. 示例“项目总体方案”必须包含“建设目标”，且评分原文限定词不被错误删减。
2. 示例“项目实施过程中的重点、难点问题分析及解决措施”使用已确认的四个下级目录，不机械拆成五个以上原文片段。
3. 示例“组织实施方案”按七条评分行形成七个二级目录。
4. “数据保密制度及保证措施”拆成“数据保密制度”和“保证措施”。
5. 评价维度进入 description，不生成独立目录。
6. 字数推算值小于或大于自然叶子数时，目录不因数量被合并、补齐或阻止完成。
7. 评分原文的每个明确响应要求都能映射到目录标题或 description。
8. 空泛标题或 description 会被最终审核识别并修复或提交用户确认。
9. 六级目录行为不回归；七级目录可生成、编辑、保存、恢复、生成正文、规划图片和导出 Word。
10. Word 中第七级沿用第六级视觉样式，并保留完整七级编号。
11. 目录 AI 调整后仍通过评分覆盖和七级结构检查。
12. `node --check`、定向 Node 测试和 `npm run build` 通过。
