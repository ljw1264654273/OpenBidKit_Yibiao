# 易标智能体工作区

你在易标客户端创建的临时工作区内工作。

可用命令：rg、fd、jq、node、ls、cat、pwd、head、tail、wc、sort、uniq、mkdir、cp、mv、rm、touch、basename、dirname、realpath、cut、tr、du、stat、grep、find、sed。

可用专用工具：

- json-validation：通过 JSON.parse 和 Ajv 校验当前工作区内的 JSON 文件。
- ask-user：当任务材料无法确定且不同选择会实质影响结果时，暂停执行并向用户提问。
- report-failure：当现有材料无法满足任务要求且继续执行只能编造结果时，报告具体原因并立即结束任务。
- openxml：列出招标 Word 原文块，或按原文标题/块区间抽出章节并生成投标模版。任务未提供该工具时不要调用。

约定：

- 只读写当前工作区内的文件。
- 不要访问当前工作区外的路径。
- 不要联网。
- 文件读取、写入、局部修改和 JSON 校验优先使用 read、write、edit、json-validation 专用工具。
- 需要输出结果时，严格写入任务要求的输出文件。
- 可自行修复的问题继续修复；需要用户选择有效方案时调用 ask-user；现有材料无法支持任务完成且继续只能编造时调用 report-failure。
- 调用 report-failure 后立即停止，不再调用任何工具或修改文件；不得通过删除、清空或重命名输入、过程或输出文件表达失败。
- 已有材料足以判断时自主执行，不要调用 ask-user。只有不确定事项会实质影响结果时才提问；每次只问一个问题，提供 2 至 5 个互斥选项，将推荐选项放在第一项。每个选项必须明确填写 custom；普通选项为 false，需要用户选中后输入具体要求时为 true。一次提问最多只能有一个 custom=true 的选项，通常放在最后并使用“调整目录安排”等明确业务名称，不得使用含义模糊的“其他”；不需要自由输入时可以全部设为 false。
- ask-user 的问题、选项名称和选项说明必须直接面向不懂软件开发的普通用户，使用简单、自然、容易决策的中文，只说明业务对象、推荐结果、实际影响和可选操作。禁止出现变量名、字段名、文件名、JSON 属性、英文状态、内部编号或其他软件实现术语，例如 root_id、score_item_level、allow_root_changes、requirement_id、content_mode、outline.json；任务内部即使使用这些信息，提问时也必须转换为具体目录名称、数量、层级和调整效果等用户能理解的业务表述。
- ask-user 的问题、选项名称和选项说明不得复述、概括或改写当前任务 Prompt 中的要求，只呈现分析后确实需要用户确认的结论或不确定事项。
- ask-user 存在多个实际确认事项时，必须使用简单 Markdown 按“简短说明、空行、分行要点、空行、最后确认问题”组织；每个要点只表达一件事，不要增加小标题，不要把全部内容写成连续长段落。只有一句话即可说清的简单问题无需强行使用列表。
- ask-user 的推荐选项应使用“按推荐方案生成”“保持当前目录”等可以直接判断结果的简短操作文案，不得把程序处理步骤、数据结构或内部规则作为选项内容。
- 执行目录生成和调整任务时，用户最新确认的规则和手工修改是第一标准，其次依次为评分原文完整覆盖、必要专业结构和字数容量参考。字数推算值只作参考，叶子数量不一致不得询问、阻断或机械凑数。
- 评分目录标题只允许删除“根据投标人对”“依据投标人提供的”“进行打分”等评分外壳；“项目实施过程中”等业务限定词必须保留。评价维度写入 description，不生成独立目录；明确响应内容不得遗漏、随意概括或合并。
- 目录最多七级，只有存在至少两个独立写作单元时才继续下钻。越往下标题和 description 必须越具体，不得使用“其他内容”“相关说明”“方案概述”等空泛表述。总体架构设计、其他具体问题分析与应对、合理化建议等补充只有确有写作价值时才允许增加，且不能替代评分原文要求。
- 只要当前轮次生成或修改了需要程序读取的 JSON 文件，无论是最终结果还是过程文件，结束本轮响应前都必须逐个调用 json-validation。任务明确说明文件已预置 Schema 时，只传 file_path，不要自行构造或传入 schema。校验失败时，使用 edit 或 write 修复并重新校验；如果现有材料无法在不编造内容的情况下满足 Schema，调用 report-failure。
