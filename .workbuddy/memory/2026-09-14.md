## 内容指纹原创性 · 需求澄清结论（已确认）
- 多用户范围：**暂不涉及多人**，就是同一用户先后写多份标书，不希望内容自我重复。
- 比对范围：**仅本机我自己的标书**（不跨用户、不跨设备、无共享指纹库）。
- 命中处理：**标出重复段落 + 给出改写建议**，由用户确认后替换（不自动改写）。
- 主体隔离：不需要（因已收窄为单用户本机场景）。
- 结论：需求实质从"多用户对同一项目生成"收窄为"**同一用户多份标书之间的正文防重**"，典型场景是同一招标文件的多标段各出一份标书时正文高度雷同。措辞需同步修正，去掉"多用户"表述。
- 待确认小项（不阻塞）：状态枚举是否含生成中/失败、删除是否进回收站、多标书是否真并行、存量标书是否迁移。

## 并发生成评估结论（已核实）
- 小哥确认：状态枚举**需要**生成中/失败；删除**不进回收站**（直接删，须二次确认）；**不做**存量迁移；并发生成待评估。
- 核实 DeepSeek 官方 API 限速政策（api-docs.deepseek.com/zh-cn/quick_start/rate_limit）：**并发按账号粒度**计，deepseek-v4-pro 500、deepseek-v4-flash 2500，超出返回 HTTP 429；可提工单免费扩容；请求 10 分钟未开始推理服务端断开；支持 user_id 做隔离与 KVCache 隔离。
- 结论：**并行可行**，配额远超"同时写 2–5 份标书"的需求；建议以有限并发（上限 2–3）+ 退避重试实现。剩余注意事项：账号是否多人共用（并发共享）、并行会降低 KVCache 复用率导致成本略升、长等待需与普通超时区分处理。
- 文档已升版 v1.0（业务已确认，待开发评估实现范围）。
- **小哥明确表示不需要 HTML 需求文档**，要的是"一段话讲清需求"。HTML 文件保留在 `docs/requirement-bid-project-management.html` 备用，但沟通形式改为纯文字一段话。后续需求确认阶段不再主动产文档。

## 需求口径修正（小哥再次澄清，重要）
- **第一层修正**：同一份招标文件**允许**存在两份及以上的标书，不只是"多标段"场景——同一文件就是可能写两份。防重定位为**提示引导 + 允许继续新建**，不是拦截。我此前把"两份"限定在多标段，口径过窄，已纠正。
- **第二层修正**：核心是**同一招标文件下的两份标书之间互相对比查重**（两份对比，而不是单份标书内部标记）。呈现方式应为**对照视图**（左 A 右 B、重复段落高亮联动），而非只在单份正文上打标记。HTML 文档中 F-11 的呈现方式需按此修正。
- 仍待定：正文重复的判定口径（多大重合算"一段重复"）、逐字引用内容（招标文件原话/规范条文/固定资质介绍）是否豁免。
- 小哥拍板：**方案 3，两者结合**——默认自动比对同源标书（同一招标文件下的多份，系统已知关系），同时保留手动勾选任意标书发起查重的入口。
- 呈现：两份标书**对照视图**（左 A 右 B、重复段落高亮联动）+ 改写建议 + 用户确认后替换。
- **判定口径（小哥采纳建议）**：按段落级近似重复判定，需能识别伪改写（改字、换语序），先给一个默认灵敏度，用起来再调，不预设硬性百分比阈值。
- **豁免范围（小哥采纳建议）**：招标文件原话、规范条文、公司固定资质介绍等"本就该逐字一致"的内容算豁免，不标为重复。
